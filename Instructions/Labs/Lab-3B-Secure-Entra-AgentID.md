# Microsoft Entra エージェント ID をセキュリティ保護する

あなたの組織の開発チームは、人事データを含む SharePoint サイトへの読み取りアクセス権を持ち、ユーザーの代わりに予定表の招待を送信できる Copilot Studio エージェントをデプロイしました。 どのようなときにエージェントが認証できるかを管理する条件付きアクセス ポリシーはなく、エージェント ID が侵害された場合に攻撃者が実行できることを誰も評価していません。

あなたは、セキュリティ レビュー要求で、次のリスク評価サイクルの前に、エージェント ID にガバナンス制御を適用し、その影響範囲を特定するように求められています。

このラボでは、次のことを行います。

- Microsoft Entra ID でエージェント ID を特定し、それがユーザー ID やサービス プリンシパルとどのように異なるかを理解する
- すべてのエージェント ID を対象とするリスクベースの条件付きアクセス ポリシーを作成する
- エージェントのユーザー アカウントを対象とする 2 つ目の条件付きアクセス ポリシーを作成し、このスコープに対する許可制御として MFA を利用できない理由を理解する
- Microsoft Defender XDR を使ってエージェントの影響範囲を分析する
- Microsoft 365 管理センターでエージェントの構成済みの接続を管理する
- Copilot Studio でエージェントのリアルタイム保護を有効にする

この演習の所要時間は約 **60** 分です。

> **注意**: このラボでは、シード グローバル管理者である 1 つのアカウント **User1** (`sc500-user1-`) を使って、4 つの異なるポータル (Microsoft Entra 管理センター、Microsoft Defender XDR、Microsoft 365 管理センター、Copilot Studio) にアクセスします。 このアカウントに指定した認証情報を使用してください。

## Microsoft Entra ID でエージェント ID を見つける

すべての Copilot Studio エージェントは、ユーザー、サービス プリンシパル、マネージド ID とは別の ID の種類として Microsoft Entra ID に登録されます。 セキュリティ制御を適用する前に、エージェント ID オブジェクトがディレクトリ内でどのように表されるかを理解する必要があります。

1. **管理者**資格情報を使って、**Microsoft Entra 管理センター** (`https://entra.microsoft.com`) にサインインします。

1. 左側のナビゲーションで、**[Entra ID]** > **[エージェント]** > **[エージェント ID]** を参照します。

    > **注意**: **[エージェント]** は、人間以外の AI の ID を管理するための Entra 管理センターの専用ハブです。 **[アプリケーション]** ([アプリの登録] と [エンタープライズ アプリケーション] が含まれます) とは別です。 **[エージェント]** の下には **[エージェント ID]**、**[エージェント ブループリント]**、**[サインイン ログ]**、**[概要]** があります。 エージェント ID には、エージェントの目的、構成済みの接続、それをデプロイしたチームなど、標準的なサービス プリンシパルにはない追加のメタデータが含まれます。

1. 一覧で **sc500-copilot-agent** を見つけて選び、ID の詳細を開きます。

1. エージェント ID のプロパティを確認します。 次のことを考慮してください。

    | フィールド | 内容 |
    |-------|------------------|
    | **オブジェクトの種類** | AgentIdentity — User、Application、または ServicePrincipal とは異なります |
    | **つながり** | このエージェントがアクセスすることを認可されているデータ ソースとサービス |
    | **Created date (作成日)** | エージェントがテナントに登録された時 |

1. 左側のナビゲーションで、**[ユーザー]** を展開して **[すべてのユーザー]** を選びます。

1. ユーザーの一覧で **sc500-copilot-agent** を検索します。

    標準ユーザーのアカウントと共にそのエージェントのエントリが見つかるはずです。 これはエージェントの**ユーザー アカウント**であり、エージェントでメールボックス、Teams プレゼンス、またはユーザー タイプのオブジェクトを必要とするリソースが必要になると Entra ID によって作成される、2 番目の別のディレクトリ オブジェクトです。

    > **注意**: このラボで最も重要な概念はデュアル オブジェクト モデルです。 すべての Entra エージェント ID は、**エージェント ID** サービス プリンシパル ([エージェント ID] で確認したもの) を持ち、必要に応じて**エージェントのユーザー アカウント** ([すべてのユーザー] で確認したもの) を持つ場合があります。 これらは、2 つの異なる条件付きアクセス ポリシー ターゲットを必要とする 2 つの個別のディレクトリ オブジェクトです。 さらに重要なのは、**すべてのユーザー**を対象とする既存の CA ポリシーが (組織のベースライン MFA ポリシーを含みます)、エージェントのユーザー アカウントにも適用されることです。 エージェントは MFA チャレンジを満たすことができないため、"すべてのユーザーに MFA を要求する" ポリシーによってエージェントは完全にブロックされます。 これを中心とする設計は、次のタスクの一部です。

## エージェント ID のための条件付きアクセス ポリシーを作成する

人間以外の ID を対象とする条件付きアクセス ポリシーは、ユーザーに対するポリシーとは動作が異なります。 エージェント ID は対話型のチャレンジ (MFA、デバイス コンプライアンス プロンプト) を満たせないため、利用可能な許可制御は**ブロック**または**許可**に限定されています。 関連する条件はリスク シグナルであり、場所や認証方法ではありません。

2 つのポリシーを作成します。1 つはエージェント ID (サービス プリンシパル オブジェクト) 用で、もう 1 つはエージェント ユーザー アカウント (すべてのユーザーのユーザー タイプ オブジェクト) 用です。 これら 2 つのスコープは、異なるディレクトリ オブジェクトの種類を対象としているため、個別のポリシーが必要です。

### ポリシー 1 — 高リスクのエージェント ID のサインインをブロックします

1. Entra 管理センターで、**[保護]** を展開して **[条件付きアクセス]** を選びます。

1. **[新しいポリシーの作成]** を選択します。

1. **[名前]** フィールドに次のように入力します。

    ```input
    sc500-agent-risk-block
    ```

1. **[割り当て]** で、**[ユーザーまたはエージェント (プレビュー)]** を選びます。

1. **[このポリシーは何に適用されますか?]** ドロップダウンで、**[エージェント (プレビュー)]** を選びます。

1. **[含める]** で、**[エージェントの選択]** を選びます。

1. 一覧で **sc500-copilot-agent** にマークを付けてから、**[選択]** を選びます。

1. **[アクセス制御]** で **[許可]** を選択します。

    - **[アクセスのブロック]** を選びます
    - **選択**を選択します。

1. **[ポリシーの有効化]** で、 **[オン]** を選択します。

    > **注意**: 適用を検証するために中リスクまたは高リスクのエージェント サインイン イベントをトリガーするのはラボ環境では実用的でないため、このポリシーは **[レポート専用]** に設定されています。 運用テナントでは、What If ツールの出力を調べてエージェントの正当な操作がブロックされないことを確認した後、**[オン]** に切り替えます。

1. **［作成］** を選択します

### ポリシー 2 — エージェントのユーザー アカウントのアクセスを管理します

1. **[新しいポリシーの作成]** を選択します。

1. **[名前]** フィールドに次のように入力します。

    ```input
    sc500-agent-user-block
    ```

1. **[割り当て]** で、**[ユーザーまたはワークロード ID]** を選択します。

1. **[このポリシーは何に適用されますか?]** ドロップダウンで、**[ユーザーとグループ]** を選びます。

1. **[含める]** で、**[ユーザーとグループの選択]** を選んでから、**[すべてのエージェント ユーザー]** をオンにします。

    > **注意**: **[すべてのエージェント ユーザー]** は、標準ユーザー アカウントを含めずにエージェント ユーザー アカウントを対象とする専用のスコープです。 代わりに **[すべてのユーザー]** をターゲットにした場合、ポリシーは人間のユーザーもカバーし、適用しようとしている許可のブロックによってテナント内のすべてのユーザーがロックアウトされます。

1. **[アクセス制御]** で **[許可]** を選択します。

    - **[アクセスのブロック]** を選びます
    - **選択**を選択します。

    > **注意**: **[多要素認証を要求する]** はこのスコープの許可オプションとして使用できないことにご注意ください。 これは仕様であり、エージェントのユーザー アカウントは MFA プロンプトに応答できない人間ではない ID です。 ブロックが唯一の意味のある適用オプションです。 これは、前に説明した CA トラップに対する答えでもあります。ベースラインの "すべてのユーザーに MFA を要求する" ポリシーによってエージェントのユーザー アカウントがキャッチされた場合、エージェントは通知なしにブロックされ、プロンプトは表示されません。 正しい設計は、ここで行っているように、エージェントのユーザー アカウントに対する適用のスコープを別に設けることです。

1. **[ポリシーの有効化]** で、 **[オン]** を選択します。

1. **［作成］** を選択します

1. **[条件付きアクセス]** ポリシーの一覧に戻り、**sc500-agent-risk-block** と **sc500-agent-user-block** の両方が一覧に含まれることを確認します。

## Copilot Studio でリアルタイム保護を有効にする

リアルタイム保護は、実行中のエージェントの動作を監視し、定義されているポリシーから外れたアクションをブロックしたり、フラグで示したりできます。 これは、エージェントがサインインするときではなく実行しているときに作動する実行時の動作制御であり、前に構成した条件付きアクセス制御を補完します。

1. 新しいブラウザー タブを開いて、[Copilot Studio](https://copilotstudio.microsoft.com) に移動します。

1. ページの上部にある環境セレクターで、現在正しいテナント環境にいることを確認します。

1. 左側のナビゲーションで **[エージェント]** を選んだ後、**sc500-copilot-agent** を見つけて選びます。

1. エージェントの設定で、**[セキュリティ]** タブを選びます。

    > **注意**: 環境内の Copilot Studio のバージョンによっては、**[詳細設定]** として、または **[セキュリティとコンプライアンス]** セクションに、表示される場合があります。 ターゲットの設定として **[リアルタイム保護]** を探します。

1. **[リアルタイム保護]** 設定を見つけて、それを **[有効]** に設定します。

1. 保護のオプションを調べて、以下のものがアクティブであることを確認します。

    | 保護オプション | 機能 |
    |------------------|-------------|
    | **コンテンツ モデレーション** | 構成されているコンテンツ ポリシーに実行時に違反したエージェントの応答をブロックする |
    | **データ損失の防止** | エージェントが承認されたチャネルの外部で機密コンテンツを共有するのを禁止する |
    | **異常検出** | エージェントの異常な動作パターンにセキュリティ チーム レビューのためのフラグを設定する |

1. **[保存]** を選んで、リアルタイム保護の設定を適用します。

    > **注意**: リアルタイム保護は、時間をかけてエージェントの動作ベースラインを構築します。 早期のアラートについては、レビューを行って、正当なエージェントの動作と異常を区別することが必要になる場合があります。 Microsoft Defender XDR でフラグの付いたイベントをレビューします。そこでは、Copilot Studio のリアルタイム保護からのエージェント セキュリティ アラートが、他の ID アラートと共に表示されます。

## まとめ

このラボでは、4 つのポータルで Copilot Studio エージェント ID を使って、階層化されたガバナンス制御のセットを適用しました。

Microsoft Entra ID では、エージェントのデュアル オブジェクト モデル (エージェント ID のサービス プリンシパルと、[すべてのユーザー] でのエージェントのユーザー アカウント) を確認し、その 2 つのオブジェクト構造による CA ポリシーの設計への影響を理解しました。 2 つの条件付きアクセス ポリシーを作成しました。1 つはすべてのエージェント ID を対象とするリスクベースのブロック ポリシーで、もう 1 つはエージェントのユーザー アカウントを対象とするブロック専用ポリシーです。また、MFA が人間以外の ID に対する許可制御として使用できない理由について注意しました。

Microsoft Defender XDR では、**sc500-copilot-agent** の影響範囲を分析し、エージェントが侵害された場合の攻撃面を表す 2 つの攻撃パス (機密性の高い人事データへの SharePoint アクセスと、委任された予定表アクセス) を確認しました。

Microsoft 365 管理センターでは、**sc500-ai-datastore** へのエージェントの SharePoint 接続を無効にして、影響範囲分析で特定された高リスクの攻撃パスを削除しました。

Copilot Studio では、リアルタイム保護を有効にして、ID ガバナンス制御の上位に実行時動作監視レイヤーを追加しました。

この演習は無事に完了しました。

1. Entra 管理センター > **[保護]** > **[条件付きアクセス]** に移動します。
1. **sc500-agent-risk-block** を選び、**[削除]** を選んで確認します。
1. **sc500-agent-user-block** を選び、**[削除]** を選んで確認します。
