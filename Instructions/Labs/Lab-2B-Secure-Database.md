# Azure SQL Database をセキュリティで保護する

あなたの組織の AI アプリケーション データベースへの侵入テストで、3 つの重要な結果が見つかりました。 1 つ目は、データベース サーバーは SQL 認証のみを使用しており、データベースの資格情報を保持しているユーザーについての ID ガバナンスがなく、管理アクセスのための Entra ID 監査証跡もないということです。 2 つ目は、**Azure サービスとリソースにサーバーへのアクセスを許可する**というファイアウォール例外が有効になっているため、所有権や場所に関係なく Azure でホストされるすべてのサービスがデータベースにアクセスできるバイパスが作成されています。 3 つ目は、サーバーには監査機能が設定されていないため、誰がいつどのデータを照会したかという記録がありません。

あなたのタスクは、3 つの結果すべてに対処することです。 SQL のみの認証をセキュリティ グループに基づく Entra ID 管理者 ID に置き換え、Azure サービスのファイアウォールのバイパスを削除し、データベースをプライベート エンドポイントに分離し、Log Analytics ワークスペースへの監査を有効化し、Defender for Databases を有効にします。

このラボでは、次のことを行います。

- Entra ID セキュリティ グループを作成し、これを SQL サーバーの Entra ID 管理者として設定する
- Azure サービスのファイアウォール例外を無効にし、プライベート エンドポイントを設定する
- Log Analytics ワークスペースへの SQL 監査を有効にする
- クエリを実行して監査可能なイベントを生成し、Log Analytics で確認する
- Defender for Databases を有効にする

この演習の所要時間は約 **60** 分です。

## Microsoft Entra ID 認証を構成する

SQL のみの管理者アカウントを使用するということは、データベース アクセスを Entra ID 条件付きアクセス、PIM、またはサインイン リスク ポリシーを使って制御できず、資格情報が ID プラットフォームから独立して存在するということを意味します。 SQL 管理者を Entra ID セキュリティ グループに置き換えるとこの課題に対処できます。つまり、グループ メンバーシップは Entra ID で管理され、Entra サインイン ログを使用してアクセスを監査でき、グループ自体はアクセス レビューによって管理されます。

`sc500-sql-admins` という名前のセキュリティ グループを作成し、`sc500-user06` をメンバーとして追加し、そのグループを `sc500-lab2b-sql` の Entra ID 管理者として設定します。

1. **Microsoft Entra 管理センター** (`https://entra.microsoft.com`) に**グローバル管理者**資格情報を使ってサインインします。

1. 左側のメニューで **[グループ]** を展開し、**[すべてのグループ]** を選択します。

1. **[新しいグループ]** を選びます。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **グループの種類** | セキュリティ |
    | **グループ名** | `sc500-sql-admins` |
    | **グループの説明** | sc500-lab2b-sql の Entra ID 管理者グループ |
    | **メンバーシップの種類** | 割り当て済み |

1. **[メンバー]** には **[メンバーが選択されていません]** を選択します。

1. **user-2** を検索して選択し、**[選択]** を選択します。

1. **［作成］** を選択します

    > **注**: SQL Entra ID 管理者として個別アカウントではなくグループを使用することで、アクセス管理が一元化されます。管理者の追加と削除はグループ メンバーシップを介して行われ、SQL サーバーの設定を変更する必要はありません。 また、グループへのアクセス レビューにより、すべてのメンバーに引き続きデータベース管理者アクセス権が必要であることを定期的に確認することもできます。

1. **Azure portal** (`https://portal.azure.com`) に移動します。

1. 検索バーで、`SQL server` を検索して選択します。

1. **[sc500-lab2b-sql]** を選択します。

1. 左側のメニューの **[設定]** で、**[Microsoft Entra ID]** を選択します。

1. **[管理者の設定]** を選びます。

1. **sc500-sql-admins** を検索して選択し、**[選択]** を選択します。

1. **[保存]** を選択します。

    **[Microsoft Entra 管理者]** フィールドに `sc500-sql-admins` が表示され、選択肢として **[Microsoft Entra 認証のみ]** が利用可能になっていることを確認します。

    > **注**: **[Microsoft Entra 認証のみ]** を有効にすると SQL 認証は完全に無効になり、SQL ログイン認証は使用できなくなります。 これは最も安全な構成ですが、Entra ID 認証を有効にする前に、データベースに接続するすべてのアプリケーションやサービスが Entra ID 認証をサポートしていることを確認する必要があります。 このラボでは、後の手順でポータル クエリ エディターが接続できるように、混合認証をそのまま使用します。

## ネットワーク アクセスを制限し、プライベート エンドポイントを設定する

**Azure サービスとリソースにサーバーへのアクセスを許可する**例外は、独自のサービスだけでなく、あらゆるサブスクリプションまたはテナントからあらゆる Azure サービスへのデータプレーン アクセスを許可します。 これは初期展開時の利便性のために有効化された可能性が高い広範なバイパスです。 それを削除し、その後プライベート エンドポイントを作成して、制御された VNet スコープでデータベースへのアクセスを提供します。

1. **[プライベート アクセス]** タブを選択します。

1. **[+ プライベート エンドポイントの作成]** を選択します。

1. **[基本]** タブで次の値を構成します。

    | 設定 | 値 |

    | **リソース グループ** | sc500-lab2b-rg |
    | **名前** | `sc500-sql-pe` |
    | **リージョン** | 米国東部 |

1. **[次へ: リソース]** を選択します。

1. **[リソース]** タブで、次の情報が事前に入力されていることを確認します。

    | 設定 | 値 |

    | **リソース** | sc500-lab2b-sql |
    | **ターゲット サブリソース** | sqlServer |

1. **[次へ: 仮想ネットワーク]** を選択します。

1. **[仮想ネットワーク]** タブ上で、次のように構成します。

    | 設定 | 値 |

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

    プライベート エンドポイントの展開が完了するまで待ちます。通常、1、2 分かかります。

## SQL 監査を有効にして監査可能なイベントを生成する

SQL 監査では、永続的な保存先にクエリ、ログイン、スキーマの変更、エラーなどのデータベースレベルのすべてのイベントが記録されます。 監査がなければデータアクセスは記録されません。つまり、"火曜日の午前 2 時にモデルのメタデータ テーブルに対して SELECT を実行したのは誰ですか?" という質問に答えられません。 Log Analytics の監査を使用すると、KQL を使用してその履歴に対してクエリを実行し、異常なパターンに関してアラートを作成できます。

> **注**: 前の手順に戻ってパブリック SQL エンドポイントを無効にする**前に**、ポータル クエリ エディターで SELECT クエリを実行する手順を含めて、このセクション全体を完了します。 パブリック エンドポイントが無効になると、ポータル クエリ エディターは接続できなくなります。

1. 左側メニューの **[sc500-lab2b-sql]** の **[セキュリティ]** の下の **[監査]** を選択します。

1. **[Azure SQL 監査を有効にする]** を **[オン]** に設定します。

1. **[監査ログの保存先]** で **[Log Analytics]** を選択します。

1. ラボのサブスクリプションを選択し、Log Analytics ワークスペースとして **sc500-lab2b-log** を選択します。

1. **[保存]** を選択します。

    > **注**: サーバーレベルの監査は、`ai-workload-db` を含むサーバー上のすべてのデータベースに適用されます。 データベース レベルで監査を個々に設定する必要はありません。

1. `sc500-lab2b-sql` の左メニューの **[設定]** で、**[SQL データベース]** を選択します。

1. **ai-workload-db** を選択してデータベースを開きます。

1. `ai-workload-db` の左側のメニューの **[クエリ エディター]** の下の **[クエリ エディター (プレビュー)]** を選択します。

1. [認証] パネルで、**[SQL Server 認証]** を選択します。 次の資格情報を入力します。

    | フィールド | 値 |
    |-------|-------|
    | **Login** | sc500sqladmin |
    | **パスワード** | SC500Lab2b! |

    クライアント IP をファイアウォールに追加するよう求められたら、**[クライアント IP の追加]** を選択し、**[OK]** を選択して、同じ資格情報でもう一度認証します。

    > **注**: グローバル管理者アカウントにはデータベース アクセス権がありません。`sc500-sql-admins` Entra ID 管理者グループのメンバーのみにアクセス権があります。 SQL Server 認証は、サーバーがプロビジョニングされたときに作成された組み込みの SQL 管理者アカウントを使用します。このアカウントは Entra ID グループ メンバーシップに関係なくアクセス権があります。

1. クエリ エディターで、次のクエリを実行します。

    ```sql
    SELECT * FROM AiModelMetadata;
    ```

    3 行が返されることを確認します。 このクエリは、Log Analytics ワークスペースに表示される監査可能なイベントを生成します。

    > **注**: 監査可能なクエリを生成したので、パブリック エンドポイントの無効化に進むことができます。 そのステップを完了すると、ポータル クエリ エディターにアクセスできなくなりますが、これは想定されている安全な設定です。

1. ポータルの **sc500-lab2b-sql** に戻ります。

1. 左側のメニューの **[セキュリティ]** で、**[ネットワーク]** を選択します。

1. **[パブリック アクセス]** タブを選択します。

1. **[パブリック ネットワーク アクセス]** を **[無効]** に設定します。

1. **[保存]** を選択します。

    > **注**: パブリック エンドポイントが無効になり、プライベート エンドポイントが設定されたため、SQL Server には `sc500-lab2b-vnet`内のリソースからのみアクセスできるようになりました。 ポータル クエリ エディターは接続できなくなりますが、これは想定されており、ネットワークの分離が正しく機能していることを示しています。

### Log Analytics で監査ログを検証する

セキュリティ エンジニアは監査を有効にするだけでなく、活動が記録されていることを確認します。 このタスクでは、先ほど実行した `SELECT * FROM AiModelMetadata` ステートメントが記録されていることを確認するために Log Analytics にクエリを実行します。 結果により、監査パイプライン全体 (SQL サーバーがイベントをキャプチャし、Log Analytics に転送し、データがクエリ可能である) が正常に動作していることが確認できます。

Log Analytics のインジェストは、通常、イベントが生成された後、2 から 5 分かかります。

1. **[ホーム]** を選択して Azure の [概要] ページに戻ります。

1. Azure portal の検索バーで、**Log Analytics ワークスペース**を検索して選択します。

1. **[sc500-lab2b-log]** を選択します。

1. 左のメニューで **[ログ]** を選択します。

1. **[クエリー]** ダイアログが表示されたら閉じます。

1. ページの右上隅にあるモード ドロップダウンを選択し、**[簡易モード]** から **[KQL モード]** に切り替えます。 これにより KQL クエリ エディターが開きます。

1. 空白のクエリの領域をクリックし、次の KQL クエリを貼り付けます。

    ```kusto
    AzureDiagnostics
    | where Category == "SQLSecurityAuditEvents"
    | where statement_s contains "AiModelMetadata"
    | project TimeGenerated, server_instance_name_s, database_name_s, statement_s, client_ip_s
    | order by TimeGenerated desc
    ```

1. クエリの上にある **[実行]** を選択します。

    `SELECT * FROM AiModelMetadata` ステートメントを示すエントリが表示されることを確認します。 結果が表示されない場合は、2、3 分待ってから、もう一度 **[実行]** を選択します。

    > **注**: 5 分経っても結果が表示されない場合は、`sc500-lab2b-sql` の監査設定が **[オン]** と表示されていることと、Log Analytics ワークスペースが `sc500-lab2b-log` と一致していることを確認します。 サブスクリプションの負荷が高い場合、最大 10 分のインジェスト遅延が発生する可能性があります。

## Defender for Databases を有効にする

Defender for Databases は、SQL サーバーに継続的な脅威検出を提供します。SQL インジェクションの試み、ブルートフォースログイン攻撃、異常なアクセス パターン、データ流出の兆候を特定します。 監査が起こったことを記録するのとは異なり、Defender は疑わしい活動が検出されるとリアルタイム アラートを生成します。

1. Azure portal の検索バーで、`Microsoft Defender for Cloud` を検索して選択します。

1. 左側のメニューの **[管理]** で、**[環境設定]** を選択します。

1. サブスクリプションを展開して選択します。

1. **[Defender プラン]** ページで **[データベース]** を見つけて **[オン]** に設定します。

1. **Azure SQL Database** が保護されるリソース タイプに含まれていることを確認します。

1. **[保存]** を選択します。

    > **注**: Defender for Databases を有効にした後、`sc500-lab2b-sql` が Defender for Cloud のデータベース セキュリティ ビューに保護されるリソースとして表示されるまでに、**5 から 15 分**かかる場合があります。 これは正常な動作です。Defender for Cloud はプランが有効化された後、PaaS リソースを非同期的に発見し分類します。 ラボを終了する場合、この発見が完了するのを待つ必要はありません。リソースがポータル ビューに表示される前に、プランは既に有効になっています。

1. Azure portal の **sc500-lab2b-sql** に戻ります。

1. 左側のメニュー ウィンドウの **[セキュリティ]** で、**[Microsoft Defender for Cloud]** を選択します。

    このサーバーの Defender for Cloud の状態が **[オン]** または **[保護されています]** になっていることを確認します。 **[保護されていません]** と表示されている場合は、5 分待ってから更新します。

## まとめ

このラボでは、侵入テストで 3 つの重要なセキュリティ上の結果が得られた Azure SQL データベースを強化しました。

SQL のみの認証をグループに基づく **Entra ID 管理者** (`sc500-sql-admins`) に置き換え、資格情報ベースのデータベース アクセスへの依存を排除し、条件付きアクセス、サインイン リスク ポリシー、アクセス レビューなどの Entra ID ガバナンスをデータベース管理者アクセスに適用できるようにしました。

Azure でホストされるあらゆるサービスに対して広範なバイパスを作った **Azure サービスを許可する**ファイアウォール例外を削除し、`sc500-lab2b-vnet` サブネットへの接続を制限するために**プライベート エンドポイント**を展開しました。 その後、パブリック エンドポイントが無効化され、データベースはパブリック インターネットや認可された VNet 以外の Azure サービスからアクセスできなくなりました。

Log Analytics ワークスペースへの **SQL 監査**を有効にし、監査パイプラインがデータベースの活動を捉えていることを確認するテスト クエリを生成しました。 その後、KQL クエリを使って監査イベントが Log Analytics に表示されたことを確認しました。 最後に、**Defender for Databases** を有効にし、SQL インジェクション、ブルートフォース攻撃、異常アクセス パターンに対するリアルタイムの脅威検出を可能にしました。

# レビュー: プライベート エンドポイント接続性検証タスクを追加する

## これによりもたらされること

プライベート エンドポイントが単に設定されているだけでなく、機能的であることを証明するタスクです。 パブリック アクセスを無効にした後、クラウドおよび AI セキュリティエンジニアは、VNet 内の認可済みリソースがデータベースにアクセスでき、外部のリソースはアクセスできないことを確認する必要があります。 これにより、ラボに既に含まれている監査検証パターンと一致しています (有効化 → イベントを生成 → キャプチャされたことを確認)。

## これがまだラボに含まれていない理由

ジャンプ ボックス VM を事前プロビジョニングすると、Skillable 環境の構築に VM のコンピューティング コストと複雑さが加わります。 現在のラボではこれを回避しています。 コストと構築期間が許容範囲内であれば、追加する価値があります。

## 変更が必要なもの

### 1. ARM テンプレート (`lab-2b-setup.json`)

ネストされたリソース グループの展開に次のリソースを追加します。

- `default` サブネット (`10.2.0.0/24`) 内に小規模な **Windows VM**(`sc500-lab2b-jumpbox`、Standard_B1s)
  - パブリック IP と NSG を使用して任意のソースからの RDP (ポート 3389) を許可するか、よりクリーンでポートレスな方法として、Azure Bastion に置き換える
  - ローカル管理者: `sc500sqladmin` / `SC500Lab2b!` (簡便さのために SQL の資格情報と一致)
- **VM 上のカスタム スクリプト拡張機能** プロビジョニング時に sqlcmd をサイレント モードでインストールする (ODBC ドライバー 18 + `winget` を介した sqlcmd パッケージ、または直接 MSI でダウンロード)
- Bastion を使う場合: `sc500-lab2b-vnet` に `AzureBastionSubnet` (/26 以上) を追加し、`Microsoft.Network/bastionHosts` リソースを展開する

### 2. ラボ ガイド — "パブリック エンドポイントを無効化" した後の新しいタスク

次の手順を含む **"VNet 内部からプライベート エンドポイントの接続性を検証する"** というタスクを追加します。

1. RDP または Bastion で `sc500-lab2b-jumpbox` に接続します
2. コマンド プロンプトを開き、以下を実行します。
   ```
   nslookup sc500-lab2b-sql.database.windows.net
   ```
   解決された IP が **10.2.0.x** アドレス (プライベート エンドポイントの NIC) であり、パブリック Azure IP ではないことを確認します これはプライベート DNS ゾーンが SQL トラフィックを VNet 経由でルーティングしていることを示しています。
3. 次の sqlcmd クエリを実行します。
   ```
   sqlcmd -S sc500-lab2b-sql.database.windows.net -U sc500sqladmin -P "SC500Lab2b!" -d ai-workload-db -Q "SELECT * FROM AiModelMetadata"
   ```
   3 行が返されたことを確認します。 これにより、プライベート エンドポイントが正しくトラフィックを転送しており、SQL 認証がプライベート チャネルを通じて機能していることが証明されます。
4. **ネガティブ テスト**: `ai-workload-db` で Azure portal のクエリ エディターを開き、接続を試みてください。 接続が失敗することを確認します。 これによりループが閉じられ、アクセスは VNet 内部からのみ可能になります。

### 3. Defender for Databases の注意事項

ジャンプ ボックスの VM は PaaS リソースではないため、Defender for Databases ではカバーされません。 VM 外部から SQL 接続を試行するのではなく、外部アクセスの証明にはネガティブ テスト (ポータルのクエリ エディターのエラー) をおすすめします。

## 推定される追加内容

- ARM テンプレート: 約 80 から 120 行 (VM、NIC、パブリック IP、NSG、CSE、または Bastion リソース)
- ラボ ガイド: 約 1 つの新しいタスク、約 15 個の手順
- Skillable 環境の構築時間: VM プロビジョニングと sqlcmd のインストールで 5 から 8 分追加
