# Azure Policy とロールベースのアクセス制御を構成する

組織の AI プラットフォーム環境のコンプライアンス監査で、2 つのガバナンス ギャップが特定されました。 第一に、必要なリソースのタグ付けを強制するポリシーが存在せず、サブスクリプション内のリソースに一貫性のある `Environment` タグがないため、コストの割り当てとセキュリティ境界の追跡が信頼性に欠けます。 第二に、9 か月前に AI プラットフォーム チームを離れたチーム メンバーが、そのプラットフォームのリソース グループに対して現在も有効な共同作成者割り当てを引き続き保持しており、現在は作業しなくなったリソースに対する完全な管理アクセス権が付与されたままです。

あなたの任務は両方のギャップを埋めることです。 非準拠リソースを明らかにする組み込みのタグ付けポリシーを割り当てた後、コードとしてのインフラストラクチャを介してカスタム ポリシーをデプロイして、タグの強制をリソースグループにまで拡張します。 セキュリティ レビュー担当者向けのスコープ付きカスタム役割を作成して、それらの担当者を管理者に昇格させることなく、Defender for Cloud 態勢のデータに対する読み取りアクセスとロールの割り当てを付与します。その後、Entra ID のアクセス レビューを使用して正式に共同作成者アクセスを評価し、不要なアクセスを削除します。 最後に、リソース ロックを適用して、プラットフォームのストレージ アカウントを誤って削除されないように保護します。

このラボでは、次のことを行います。

- 組み込みの Azure Policy を割り当て、ポリシー コンプライアンスの結果を確認する
- Cloud Shell を使用し、Bicep を介してカスタムのタグ強制ポリシー定義をデプロイする
- カスタムの Azure ロールを作成し、指定されたセキュリティ レビュー担当者に割り当てる
- Entra ID のアクセス レビューを使用して、上昇特権ロールの割り当てを評価して修復する
- CanNotDelete リソース ロックを適用し、それによって削除が防止されることを確認する

この演習の所要時間は約 **60** 分です。

> **注**: このラボでは、**グローバル管理者**アカウント (あなたのプライマリ ラボ資格情報) と **sc500-user04** (指定されたレビュー担当者としてアクセス レビューの決定を完了するために使用) の 2 つのアカウントを使用します。 両方のアカウントの資格情報は、ラボ環境の **[リソース]** タブにあります。

## 組み込みのコンプライアンス ポリシーを割り当てる

Azure Policy は、定義されたルールに照らしてリソースを評価し、遵守状況を報告します。既存のリソースを変更する必要はありません。 **拒否**効果ポリシーは、非準拠リソースの新規作成をブロックします。ポリシーに既に違反している既存のリソースは、コンプライアンス レポートで**非準拠**として表示されます。 組み込みの**リソースでタグを必須とする**ポリシーを `sc500-lab1d-rg` に割り当てます。これにより、`sc500lab1d@lab.LabInstance.Id` (ストレージ アカウント) と `sc500-lab1d-vm` (仮想マシン) はどちらも `Environment` タグがないため、非準拠のフラグが設定されます。 非準拠リソースがさらにもう 1 つ表示される場合があります。これは想定された状態です。

1. **User-1** の資格情報を使用して Azure portal (`https://portal.azure.com`) にサインインします。

1. 検索バーで、**`Policy`** を検索して選択します。

1. 左側のメニューの **[作成]** で、**[割り当て]** を選択します。

1. **[ポリシーの割り当て]** を選択します。

1. **[基本]** タブで、次の設定を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **Scope** | 省略記号 (**[...]**) を選択し、お使いのサブスクリプションと、リソース グループとして **[sc500-lab1d-rg]** を選択します。 **[選択]** を選択します。 |
    | **除外** | 空白のままにします |
    | **ポリシー定義** | 省略記号 (**[...]**) を選択し、**`Require a tag on resources`** を検索して結果を選択し、**[追加]** を選択します。 |
    | **割り当て名** | SC500-require-env-tag |
    | **ポリシーの適用** | Enabled |

1. **パラメーター** タブを選択します。

1. **[タグ名]** フィールドに「`Environment`」と入力します。

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

    > **注**: ポリシー割り当てが完全に伝達されるまで最大 30 分かかる場合があります。その後、新しい割り当てがコンプライアンス評価に反映されます。 待機せずに、次の手順でオンデマンドのスキャンをトリガーします。

1. Azure portal の上部バーで、**Cloud Shell** アイコン (>_) を選択します。 シェルの種類を選択するように求められたら、**[Bash]** を選択します。 ストレージ アカウントを作成するように求められたら、サブスクリプションを選択し、**[作成]** を選択します。

1. 次のコマンドを実行して、リソース グループのオンデマンドのコンプライアンス評価をトリガーします。

    ```bash
    az policy state trigger-scan --resource-group sc500-lab1d-rg
    ```

    このコマンドは、スキャンの実行中に **IN-PROGRESS** インジケーターを表示し、スキャンが完了したときにのみ Bash プロンプトを返します。 通常、これには **5 分以上**かかりますが、サブスクリプションの負荷によってはさらに時間がかかる場合があります。  スキャンが完了するまで待つ必要はありません。 1 から 2 分待ってから、次の注と手順に進んでください。

    > **注**: コマンドの完了後もコンプライアンスの状態が**未開始**または **0 個の非準拠リソース**と表示される場合は、さらに 2 から 3 分待ってから、ポータルで **[更新]** を選択してください。 コンプライアンスの状態の更新は、スキャンの完了後に非同期に書き込まれます。

1. Azure portal で **[ポリシー]** に戻り、左側のメニューから **[コンプライアンス]** を選択します。

1. ページ上部にあるスコープ フィルターで、`sc500-lab1d-rg` を選択して、このリソース グループに絞り込みます。

1. コンプライアンスの一覧で、**[sc500-require-env-tag]** 割り当てを見つけます。

1. **`sc500lab1d@lab.LabInstance.Id`** (ストレージアカウント) と**`sc500-lab1d-vm`** (仮想マシン) が非準拠リソースの一覧に表示されていることを確認します。 リソースがさらにもう 1 つ表示される場合があります。これは想定された状態であり、ラボの結果には影響しません。

    > **注**: 両方のリソースは `Environment` タグなしでデプロイされたため、ポリシーに違反しています。 このポリシー割り当てにより、今後 `sc500-lab1d-rg` 内にデプロイされるリソースで `Environment` タグが省略されるのを防ぐこともできます。 コンプライアンス評価は非破壊的であるため、既存のリソースは稼働し続けます。

## コードとしてのインフラストラクチャを使用してカスタム ポリシーをデプロイする

割り当てた組み込みポリシーにより、個々のリソースに対してタグ要件が強制されます。 リソース グループ レベルでの補完的なポリシーにより、サブスクリプション内で作成される新しいリソース グループにも、最初からタグが確実に付与されるようになります。 ポータルでこのポリシーを構成するのではなく、サブスクリプションのスコープでカスタム ポリシーを定義して割り当てる事前作成済みの Bicep テンプレートをデプロイします。 コードとしてのインフラストラクチャを通じてガバナンス ポリシーを導入すると、バージョン管理、再現性、監査可能性が確保されます。

**sc500-lab1d-policy.bicep** ファイルは、Cloud Shell のホーム ディレクトリに事前設定されています。 このファイルは、すべてのリソース グループに対して **Environment** タグを必須とするカスタムの**拒否**ポリシーを定義し、サブスクリプション スコープの割り当てを作成します。

1. Cloud Shell (Bash) をまだ開いていない場合は開きます。

1. Bash ウィンドウの上部にあるメニューで、**[ファイルの管理]** ボタンを選択します。

1. **[アップロード]** を選択します。

1. **[デスクトップ]** フォルダーを参照し、**[sc500-lab1d-policy.bicep]** ファイルを選択します。

1. **[開く]** を選択して、ファイルをアップロードします。 "**ファイルが正常にアップロードされました**" メッセージを待ちます。

1. Cloud Shell (Bash) セッションで次のコマンドを実行して、カスタム ポリシーをサブスクリプション スコープにデプロイします。

    ```bash
    az deployment sub create \
      --name sc500-tag-policy \
      --location eastus \
      --template-file ~/sc500-lab1d-policy.bicep
    ```

    デプロイは通常 1 分以内に完了します。 成功すると、ターミナルに JSON 出力ブロックが表示されます。

    > **注**: `--location eastus` フラグは、リソースが作成される場所ではなく、デプロイのメタデータ レコードのリージョンを指定します。 サブスクリプション スコープの Bicep デプロイでは、作成されるリソース (ポリシー定義など) のスコープがグローバルに設定されていても、ARM メタデータの場所を指定する必要があります。

1. Azure portal で、**[ポリシー]** に移動し、左側のメニューから **[定義]** を選択します。

1. **[種類]** フィルターで、**[カスタム]** を選択します。

    **リソース グループでタグを必須とする**ポリシーを要求するカスタム ポリシー定義が一覧に表示されていることを確認します。 これは、Bicep テンプレートによってデプロイされた定義です。

    > **注**: この手順は、ポリシー ガバナンスのためにコードとしてのインフラストラクチャを使用する方法を示しています。 同一の Bicep テンプレートをリポジトリにコミットし、pull request によるレビューを行い、複数の環境に一貫してデプロイすることが可できます。これにより、ポータルでの手動による構成に依存せずに、ガバナンス ルールが均一かつ確実に適用されます。

1. 左側のメニューから **[割り当て]** を選択します。

    カスタムのタグ ポリシーの割り当てが一覧に表示され、スコープがサブスクリプションに設定されていることを確認します。 Bicep テンプレートにより、ポリシー定義と割り当ての両方が 1 回の操作だけでデプロイされました。

1. Cloud Shellを閉じます。

## カスタムのセキュリティ レビュー担当者ロールを作成する

**閲覧者**などの組み込みの Azure ロールは、スコープ内のすべてのリソースの種類に対する広範な読み取りアクセスを許可します。 Defender for Cloud のセキュリティ態勢データやロールの割り当ての確認など、特定のガバナンス機能のためにロールが必要な場合は、必要最小限のアクセス許可を持つカスタム役割の方が適しています。 Microsoft Defender for Cloud のデータと Azure 認証オブジェクトのみに対する読み取りアクセスを許可する **sc500-Security-Reviewer**という名前のロールを作成し、それを **User-2** に割り当てます。

1. Azure portal の検索バーで、「**リソース グループ**」を検索して選択します。

1. **[sc500-lab1d-rg]** を選択します。

1. 左側のメニューで **[アクセス制御 (IAM)]** を選択します。

1. **[+ 追加]** を選択し、**[カスタム役割の追加]** を選択します。

1. **[基本]** タブで、次の設定を構成します。

    | 設定 | Value |
    |---------|-------|
    | **カスタム ロール名** | `sc500-Security-Reviewer` |
    | **説明** | `Read-only access to Defender for Cloud security posture data and role assignments. Scoped to the sc500-lab1d-rg resource group.` |
    | **ベースラインのアクセス許可** | 最初から行う |

1. **[次へ]** を選択して、**[アクセス許可]** タブに進みます。

    > **注**: **[アクセス許可]** タブには、個々の操作を追加するための検索可能なカードベースのインターフェイスが用意されています。 ワイルドカードのアクセス許可 (たとえば `Microsoft.Security/*/read`) を追加するには、ロールの JSON を直接編集する必要があります。これは **[JSON]** タブで行います。

1. **[次へ]** を選択して **[割り当て可能なスコープ]** タブに進みます。

    **sc500-lab1d-rg** が割り当て可能なスコープとして一覧に表示されていることを確認します。 リソースグループの IAM ページからカスタム役割ウィザードを開いたため、スコープはあらかじめ設定されています。 一覧にない場合は、**[割り当て可能なスコープの追加]** を選択し、お使いのサブスクリプションを展開して **[sc500-lab1d-rg]** を選択し、**[追加]** を選択します。

1. **[次へ]** を選択して、**[JSON]** タブに進みます。

1. **[編集]** を選択して、JSON エディターを開きます。

1. `"permissions"` 配列内で行 `"actions": []` を見つけます。 空の配列を次のコードに置き換えます。

    ```json
    "actions": [
        "Microsoft.Security/*/read",
        "Microsoft.Authorization/*/read"
    ],
    ```

    完成した `"permissions"` ブロックは次のようになります。

    ```json
    "permissions": [
        {
            "actions": [
                "Microsoft.Security/*/read",
                "Microsoft.Authorization/*/read"
            ],
            "notActions": [],
            "dataActions": [],
            "notDataActions": []
        }
    ]
    ```

    > **注**: `Microsoft.Security/*/read` は、Defender for Cloud および Azure Security Center のすべてのデータ (セキュリティ評価、推奨事項、アラート、セキュア スコア) に対する読み取りアクセスを許可します。 `Microsoft.Authorization/*/read` は、すべてのロールの割り当て、ポリシー割り当て、ロール定義に対する読み取りアクセスを許可します。これにより、レビュー担当者は、書き込みまたは削除のアクセス許可を持たなくても、誰が何にアクセスできるかを監査できます。

1. **[保存]** を選択して、JSON の変更を適用します。

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

    カスタム役割が作成されるまで待ちます。 通常、これには数秒しかかかりません。

1. `sc500-lab1d-rg` の **[アクセスの制御 (IAM)]** ページで、**[追加]**、**[ロールの割り当ての追加]** の順に選択します。

1. **[ロール]** タブで、**[種類]** フィルター ドロップダウンから **[カスタム役割]** を選択し、**[sc500-Security-Reviewer]** を選択します。 [**次へ**] を選択します。

1. **[メンバー]** タブで、**[アクセスの割り当て先]** を **[ユーザー、グループ、またはサービス プリンシパル]** に設定します。

1. **[+ メンバーの選択]** を選択し、「**sc500-user04**」を検索して選択し、**[選択]** を選択します。

1. **[確認と割り当て]** を選択し、もう一度 **[確認と割り当て]** を選択して保存します。

    > **注**: `sc500-user04` は現在、`sc500-lab1d-rg` に対する `sc500-Security-Reviewer` ロールを保持しています。 これらのユーザーは、このリソース グループ内の Defender for Cloud データとロールの割り当てに対する読み取りアクセスが許可されていますが、管理または書き込みのアクセス許可はありません。 このロールは次のセクションでも使用します。`sc500-user04` は、これから作成するアクセス レビューの指定されたレビュー担当者です。

## 上昇特権アクセスを評価して修復する

`sc500-user05` は、`sc500-lab1d-rg` に対するアクティブな**共同作成者**ロールを保持しています。 この共同作成者ロールにより、完全な管理アクセス (リソースの作成、変更、削除を行う権限) は付与されますが、ロールの割り当てを管理する権限は付与されません。 このレベルのアクセスは、プラットフォーム上でアクティブに作業を行っている間は適切ですが、`sc500-user05` には、仕事上その必要がなくなりました。

**Entra ID のアクセス レビュー**は、既存のロールの割り当てが依然として適切であるかどうかを評価するための構造化された監査可能なプロセスを提供します。 `sc500-lab1d-rg` に対する共同作成者ロールを対象とするレビューを作成し、`sc500-user04` をレビュー担当者に指定した後、`sc500-user04` としてサインインして、拒否の決定を送信します。 レビューが停止すると、割り当てが自動的に削除されます。

1. Microsoft [Entra 管理センター](https://entra.microsoft.com)に移動します。

1. 左側のメニューで、**[ID ガバナンス]** を展開し、**[Privileged Identity Management]** を選択します。

1. **[Azure リソース]** を選択します。

    > **注**: リソースを検出するように求められた場合は、**[リソースの検出]** を選択し、一覧でラボのサブスクリプションを見つけて選択し、**[リソースの管理]** を選択します。 **[Azure リソース]** に戻り、お使いのサブスクリプションを選択します。

1. Azure リソースの一覧から、お使いのラボ サブスクリプションを選択します。

1. 左側のメニューで、**[管理]** の下にある **[アクセス レビュー]** を選択します。

1. **[新規]** を選択して、新しいアクセス レビューを作成します。

1. **[アクセス レビューの作成]** 画面で、レビューの **[詳細]** を次のように構成します。

    | 設定 | 値 |
    |---------|-------|
    | **レビュー名** | `sc500-contributor-review` |
    | **説明** | `Review of Contributor access on the AI platform resource group` |
    | **開始日** | 今日の日付 |
    | **頻度** | 指定日時 |
    | **期間 (日数)** | 3 |

1. **[ユーザー スコープ]** で、次の設定を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **Scope** | すべてのユーザーとグループ |
    | **Role** | `Contributor` |
    | **割り当ての種類** | アクティブな割り当てのみ |

1. **[レビュー担当者]** で、次の設定を構成します。

    | 設定 | Value |
    |---------|-------|
    | **校閲者** | 選択したユーザー |
    | **レビュー担当者の選択** | user-2  |

1. **[完了時の設定]** で、次の設定を構成します。

    | 設定 | Value |
    |---------|-------|
    | **リソースに結果を自動適用する** | Enable |
    | **レビュー担当者が応答しない場合** | 変更なし |

1. **[開始]** を選択して、アクセス レビューを作成してアクティブにします。

    > **注**: **[リソースに結果を自動適用する]** を有効にすると、レビューが停止するか、または終了日に達したときにレビューの決定が自動的に適用されます。 別途 [適用] ボタンをクリックする必要はありません。

    > **注**: アクセス レビューにより、レビュー担当者の意思決定とそれによって生じたアクセスの変更について、監査可能なタイムスタンプ付きレコードが作成されます。 運用環境では、このレコードは、SOC 2、ISO 27001、NIST 800-53 AC-6 など、定期的なアクセス認定を要求するコンプライアンス フレームワークに対するデュー デリジェンスの証拠となります。

## リソース ロックを適用する

リソース ロックは、重要なリソースの偶発的または不正な削除を防ぎます。 **CanNotDelete** ロックでは、リソースに対するすべての読み書き操作が許可されますが、所有者ロールを持つユーザーであっても削除操作がブロックされます。 ロックを `sc500lab1d@lab.LabInstance.Id` に適用し、そのロックによって削除が阻止されることを確認します。

1. Azure portal の検索バーで、「**ストレージ アカウント**」を検索して選択します。

1. [**sc500lab1d@lab.LabInstance.Id**] を選択します。

1. 左側のメニューの **[設定]** で、**[ロック]** を選択します。

1. **[+ 追加]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **ロック名** | `sc500-storage-lock` |
    | **ロックの種類** | 削除 |
    | **ノート** | `Prevents accidental deletion of the AI platform storage account.` |

1. **[OK]** を選択します。

1. 左側のメニューで、 **[概要]** を選択します。

1. **[削除]** を選択します。

1. 確認ダイアログで、ストレージ アカウント名を入力して確認し、**[削除]** を選択します。

    リソースがロックされていて削除できないことを示すエラーメッセージが表示されることを確認します。

    > **注**: `CanNotDelete` ロックは、要求元のロールに関係なく、Azure Resource Manager によって適用されます。 所有者またはサブスクリプション管理者は、ロックが設定されている間はこのリソースを削除できません。最初にロックを明示的に解除する必要があります。 これにより、意図的な摩擦が生じ、自動化されたスクリプトや正しく設定されていないパイプラインによって重要なリソースが破壊されるのを防ぐことができます。 `ReadOnly` ロックはより厳格であり、すべての書き込みおよび削除の操作がブロックされます。ただし、リソース メタデータの更新を正当に必要とするプラットフォーム操作を妨げる可能性があります。 `CanNotDelete` は、ほとんどの運用リソース保護シナリオで推奨される選択肢です。

1. [削除の確認] ダイアログを閉じます。

## まとめ

このラボでは、ポリシー コンプライアンス、コードとしてのインフラストラクチャによるポリシーのデプロイ、カスタム役割の作成、アクセス認定という 4 つの側面でガバナンス コントロールを適用しました。

**リソースでタグを必須とする**組み込みポリシーを割り当てて、`Environment` タグがない既存の非準拠リソースを明らかにし、標準の評価サイクルを待つ代わりにオンデマンドのコンプライアンス スキャンをトリガーして結果を即座に観察しました。 その後、あらかじめ作成された Bicep テンプレートを使用して、サブスクリプション スコープで補完的なカスタム ポリシーをデプロイしました。これにより、ガバナンス ルールもアプリケーションコードと同様に、コードとしてのインフラストラクチャを通じてバージョン管理でき、繰り返しデプロイできることを示しました。

セキュリティ監査担当者の職務に必要なアクセス許可 (Defender for Cloud 態勢のデータとロールの割り当てに対する読み取りアクセス) のみを持ち、それ以外のアクセス許可は持たないカスタムの Azure ロール (`sc500-Security-Reviewer`) を作成しました。 最小限の特権の原則に従い、このロールを `sc500-user04` に割り当てて、レビュー担当者がリソースに対する管理権限を持たなくてもセキュリティ状態を監視できるようにしました。

Entra ID のアクセス レビューを使用して、`sc500-user05` の現在も有効な共同作成者割り当てを正式に評価しました。 アクセスを直接削除するのではなく、レビュー プロセスを通じて、監査可能なレコード (レビューの担当者、正当な理由、結果として講じた措置) を作成しました。 この監査証跡は、定期的なアクセス認証のコンプライアンス要件を満たしています。 最後に、プラットフォーム ストレージ アカウントにリソース ロック CanNotDelete を適用しました。これにより、ID ベースのアクセス制御とリソース ロックが相互に補完的な役割を果たすことを示しました。アクセス制御は、誰が操作できるかを管理し、リソース ロックは、意図的な解除手順なしで、高度な特権を持つ ID であってもバイパスできない明示的なバリアを作成します。

この演習は無事に完了しました。
