# Azure ストレージをセキュリティで保護する

AI のトレーニング データとモデル出力を含むストレージ アカウントには、現在、ネットワーク制限なしでパブリック インターネットからアクセスできます。 最近のセキュリティ スキャンで、そのアカウントに対して脅威検出機能が有効になっておらず、アクセス トークンの発行または失効方法を制御するポリシーもないことが判明しました。 アカウント キーを持つアクター、またはポリシーに裏付けられずに生成された有効な SAS トークンを持つアクターは、監査証跡も失効パスもない状態で、トレーニング データにアクセスできます。

あなたの任務は、これらのギャップを埋めることです。 トレーニング データ コンテナーにストアド アクセス ポリシーを適用して、生成された SAS トークンを一元的に失効できるようにし、ネットワーク制限が適用される前に SAS トークンが機能することを確認し、ネットワーク アクセスを、承認された仮想ネットワークのみに制限し、その制限によって Cloud Shell からの不正なアクセスがブロックされることを確認し、将来の脅威を検出するために Defender for Storage を有効にします。

このラボでは、次のことを行います。

- BLOB コンテナーにストアド アクセス ポリシーを作成し、そのポリシーに裏付けられた SAS トークンを生成する
- ネットワーク制限の適用前と適用後に、SAS トークンを使用してデータプレーンへのアクセスを検証する
- ストレージ アカウントへのネットワーク アクセスを、承認された仮想ネットワークに制限する
- ファイアウォールが Cloud Shell および Azure portal からの不正なアクセスをブロックすることを確認する
- Defender for Servers をリソース レベルで有効にする
- Log Analytics ワークスペースの診断ログを確認する

この演習の所要時間は約 **60** 分です。

## ストアド アクセス ポリシーを作成し、SAS トークンを生成する

**ストアド アクセス ポリシー**は、コンテナー上の 1 つ以上の SAS トークンのアクセス許可と有効期間を一元化します。 ストアド アクセス ポリシーがない場合、SAS トークンを有効期限が切れる前に失効させることはできません。スタンドアロンの SAS トークンが漏洩した際の唯一の修復方法は、ストレージ アカウント キーをローテーションすることですが、これを行うと他のすべてのトークンも同時に無効になります。 ストアド アクセス ポリシーはこれを解決します。このポリシーを取り消すと、それを参照するすべての SAS トークンが即座に無効になりますが、他のアクセス パスには付帯的な影響はありません。

`training-data` コンテナーに、24 時間の読み取りアクセスを許可するストアド アクセス ポリシーを作成し、そのポリシーを参照する SAS トークンを生成します。

> **注**: 事前プロビジョニングされたストレージ アカウント名は **`sc500lab2a`** で始まり、その後にラボ サブスクリプションに固有の 8 文字のサフィックスが続きます。 このラボ全体で、`<storage-account-name>` はそのアカウントを参照します。 `sc500-lab2a-rg` リソース グループにはストレージ アカウントが 1 つだけ含まれています。このラボで `<storage-account-name>` を指定する必要がある場合はいつでもそのストレージ アカウントを選択します。

1. **User1** の資格情報を使用して Azure portal (`https://portal.azure.com`) にサインインします。

1. 検索バーで、「**ストレージ アカウント**」を検索して選択します。

1. 名前が **`sc500lab2a`** で始まるストレージ アカウントを選択します (`sc500-lab2a-rg` 内には 1 つしかありません)。

1. 左側のメニューの **[データ ストレージ]** で、**[コンテナー]** を選択します。

1. **training-data** コンテナーを選択します。

1. 左側のメニューで、**[設定]**、**[アクセス ポリシー]** の順に選択します。

    > **注**: これにより、ストレージ アカウントではなくコンテナーの **[アクセス ポリシー]** ペインが開きます。 ストアド アクセス ポリシーはコンテナー レベルで定義されます。

1. **[ストアド アクセス ポリシー]** で、**[+ ポリシーの追加]** を選択します。

1. ポリシーを次のように構成します。

    | 設定 | Value |
    |---------|-------|
    | **Identifier** | `sc500-training-read` |
    | **アクセス許可** | **[読み取り]** のみを選択します |
    | **[開始時刻]** | 現在の日付と時刻のままにします |
    | **有効期限** | 今から 24 時間に設定します |

1. **[OK]** を選択し、**[保存]** を選択してポリシーを保存します。

1. **training-data** コンテナーの概要に戻ります。

1. 左側のメニューで、**[共有アクセス トークン]** を選択します。

1. **[SAS の生成]** パネルで、次の設定を構成します。

    | 設定 | Value |
    |---------|-------|
    | **署名方法** | アカウント キー |
    | **署名キー** | キー 1 (既定値 - どちらのキーでも機能します) |
    | **ストアド アクセス ポリシー** | SC500-training-read |
    | **アクセス許可** | ポリシーから自動的に設定されます |
    | **開始日時と有効期限の日時** | ポリシーから自動的に設定されます |
    | "使用できる IP アドレス"**** | 空白のままにします |
    | **許可されるプロトコル** | HTTPS のみ |

1. **[SAS トークンと URL の生成]** を選択します。

1. **SAS トークン**の値 (SAS の URL ではありません) をコピーしてテキスト ファイルに保存します。この値は、次のセクションで必要になります。 SAS トークンはクエリ文字列のみであり、**sv=** または **si=** で始まります。 **https://** プレフィックスやコンテナー パスは含まれません。

    > **注**: この SAS トークンは、ストアド アクセス ポリシー **sc500-training-read** によって裏付けられます。 ポリシーが削除されるか、またはアクセス許可が取り消された場合、このトークンは即座に無効になります。そのため、ストレージ アカウント キーをローテーションする必要がなくなります。

## ネットワーク制限を適用する前にアクセスを確認する

ストレージ アカウントを仮想ネットワークに制限する前に、SAS トークンが Cloud Shell からのデータプレーン アクセスを提供することを確認します。 これにより、"before" 状態 (任意のネットワークからのオープン アクセス) が確立され、ファイアウォール規則が適用された後のコントラストを観察できます。

1. Azure portal の上部バーで、**Cloud Shell** アイコン (**>_**) を選択します。 メッセージが表示される場合は、**[Bash]** を選択します。

1. SAS トークンを変数に割り当て、プレースホルダーを前のセクションでコピーした SAS トークンに置き換えます。

    ```bash
    SAS_TOKEN="<paste your SAS token here>"
    ```

1. ストレージ アカウント名を変数にキャプチャします。 `sc500-lab2a-rg` リソース グループに含まれているストレージ アカウントは 1 つだけであるため、このコマンドはデプロイされた名前を直接読み込みます:

    ```bash
    STORAGE_NAME=$(az storage account list --resource-group sc500-lab2a-rg --query "[0].name" -o tsv)
    echo "Storage account: $STORAGE_NAME"
    ```

    出力には実際のアカウント名 (例: `sc500lab2aabc12345`) が表示されます。 このラボのすべての curl コマンドで `$STORAGE_NAME` を再利用します。

1. 最初の数文字をチェックして、SAS 変数が設定されていることを確認します。

    ```bash
    echo "${SAS_TOKEN:0:30}..."
    ```

    出力には、SAS トークンの先頭部分 (たとえば、`si=sc500-training-read&spr=...`) が示されます。 出力が `...` で、その前に何も示されない場合、変数は空です。SA​​S トークンの値をもう一度貼り付けて、割り当てを再実行します。

    > **警告**: 出力が `...` で、その前に何も示されない場合、変数は空です。SA​​S トークンの値をもう一度貼り付けて、割り当てを再実行します。 空の変数で処理を進めないでください。

1. 次のコマンドを実行して、SAS トークンを使用してコンテナーから BLOB を読み取ります。 これは Azure Blob Storage REST API を直接呼び出します。Azure CLI 認証は関係ありません。

    ```bash
    curl -s -w "\n--- HTTP Status: %{http_code} ---" \
      "https://${STORAGE_NAME}.blob.core.windows.net/training-data/sample-1.json?${SAS_TOKEN}"
    ```

    応答が `--- HTTP Status: 200 ---` で終わり、本文にファイルの JSON コンテンツが含まれていることを確認します。 これにより、SAS トークンが有効であり、ストレージ アカウントが現在すべてのネットワークからの読み取りアクセスを許可していることが確認されます。

    > **注**: ストアド アクセス ポリシーにより、**読み取り**アクセス許可が付与され、個々の BLOB の内容を読み取ることはできますが、コンテナーを一覧表示することはできません。 Cloud Shell は仮想ネットワークの外部で実行されるため、ここでの応答 200 により、アカウントがすべてのネットワークに対して開放されていることが確認されます。 ファイアウォール規則が適用されると、この同じ要求は 403 を返します。

## ネットワーク アクセスを、承認された仮想ネットワークに制限する

ストレージ アカウントを、**[すべてのネットワークを許可]** から **[選択されたネットワーク]** に変更し、事前にプロビジョニングされたサブネット `sc500-lab2a-vnet` を唯一の承認されたネットワークとして追加します。 その後、**[Azure サービスを許可する]** 例外を無効にします。無効にしなければ、ネットワーク メンバーシップに関係なく、Azure でホストされたあらゆるサービスのバイパスが作成されます。

1. ストレージ アカウント (**`<storage-account-name>`**) の左側のメニューで、**[セキュリティとネットワーク]** の下にある **[ネットワーク]** を選択します。

1. **[パブリック アクセス]** タブを選択し、**[管理]** を選択します。

    > **注**: **[管理]** ボタンを選択すると、**[パブリック ネットワーク アクセス]** 構成ページが開きます。 **[管理]** ボタンが表示されない場合は、既に [パブリック ネットワーク アクセス] ページが開かれている可能性があります。

1. **[パブリック ネットワーク アクセス]** で、設定が **[有効]** であることを確認します。

1. **[パブリック ネットワーク アクセス スコープ]** で、**[選択したネットワークから有効にする]** を選択します。

1. **[仮想ネットワーク]** で、**[+ 既存の仮想ネットワークの追加]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **サブスクリプション** | お使いのラボ サブスクリプション |
    | **仮想ネットワーク** | sc500-lab2a-vnet |
    | **サブネット** | default |

1. **[追加]** を選択します。

1. **[例外]** で、**[信頼された Microsoft サービスがこのリソースにアクセスすることを許可する]** のチェックボックスをクリアします。

    > **注**: **[任意のネットワークからストレージ ログへの読み取りアクセスを許可する]** チェックボックスと **[任意のネットワークからストレージ メトリックへの読み取りアクセスを許可する]** チェックボックスを有効にします。これらの例外により、VNet ファイアウォールが有効な状態でも、Azure Monitor と診断ログは機能でき、ストレージ アカウントのネットワーク構成のバイパス設定 `Logging` および `Metrics` と整合します。

    > **注**: **[信頼される Microsoft サービスを許可する]** 例外は、ネットワーク メンバーシップに関係なく、Azure Backup、Azure Site Recovery、Azure Monitor など幅広い Microsoft サービスに対して暗黙のデータプレーン アクセスを許可します。 これを無効にすると、潜在的なバイパスが閉じられて、同じテナント内の誤って構成された Azure サービスを経由したデータ流出が許可される可能性があります。 運用環境では、このバイパスを削除する前に、Azure サービスがそれを正当に必要としているかどうかを評価します。

1. **[保存]** を選択してネットワーク制限を適用します。

## ファイアウォールによって不正アクセスがブロックされることを確認する

VNet のみの制限を適用した状態で、承認された VNet の外部で実行される Cloud Shell からのストレージ アカウントへのアクセスがブロックされることを確認します。

1. **[Cloud Shell]** セッションに戻ります (または、このセッションが閉じている場合は再度開きます)。 変数 `$SAS_TOKEN` および `$STORAGE_NAME` がまだ設定されたままであるかどうかを確認します。

    ```bash
    echo "${SAS_TOKEN:0:30}..."
    echo "Storage account: $STORAGE_NAME"
    ```

    出力が空または `...` の場合、セッションはタイムアウトし、変数はクリアされました。 変数を再割当します。

    ```bash
    SAS_TOKEN="<paste your SAS token here>"
    STORAGE_NAME=$(az storage account list --resource-group sc500-lab2a-rg --query "[0].name" -o tsv)
    ```

1. 同じ BLOB 読み取り要求を実行します。

    ```bash
    curl -s -w "\n--- HTTP Status: %{http_code} ---" \
      "https://${STORAGE_NAME}.blob.core.windows.net/training-data/sample-1.json?${SAS_TOKEN}"
    ```

    応答の本文に `<Code>AuthorizationFailure</Code>` が含まれており、応答が `--- HTTP Status: 403 ---` で終了することを確認します。 `AuthorizationFailure` は、要求がネットワーク ファイアウォールによってブロックされる場合に Azure Storage から返されるエラー コードです。SAS トークンは有効ですが、要求元 (Cloud Shell の IP) は、承認されたネットワークの一覧に表示されません。 これにより、ファイアウォールがアクティブであることが確認されます。

1. Cloud Shellを閉じます。

1. ストレージ アカウント (`<storage-account-name>`) の左側のメニューで、**[ストレージ ブラウザー]** を選択します。

1. **[BLOB コンテナー]**、**[training-data]** の順に選択します。

    要求が承認されていないというエラーが表示されることを確認します。 ストレージ ブラウザーはストレージ データ プレーンを直接呼び出します。ブラウザー セッションは、承認された VNet 外部の IP アドレスから開かれているため、ここでもアクセスがブロックされます。

    > **注**: `sc500-lab2a-vnet` サブネット "内" にデプロイされたリソース (そのネットワーク内で実行されている仮想マシンなど) は、引き続きストレージ アカウントにアクセスできます。** この制限により、パブリック インターネットおよび承認された VNet 内にない他のすべてのネットワークがブロックされます。 これは、VNet 常駐ワークロードのみを対象とするストレージ アカウントのための意図されたセキュリティ態勢です。

## Defender for Storage を有効にする

Defender for Storage は、ストレージ アカウントの脅威検出を提供し、異常なアクセス パターン、マルウェアのアップロード、データ流出の試行を検出します。 これを `<storage-account-name>` のリソース レベルで有効にします。

Defender for Storage のマルウェアスキャン機能では、Azure Event Grid を使用してスキャン結果をルーティングします。 Event Grid リソース プロバイダーは、Defender for Storage を有効にする前にサブスクリプションに登録する必要があります。そうしなければ、有効化が部分的に失敗します。

1. Azure portal の上部バーで、**Cloud Shell** アイコン (**>_**) を選択します。 メッセージが表示される場合は、**[Bash]** を選択します。

1. Event Grid リソース プロバイダーを登録します。

    ```bash
    az provider register --namespace Microsoft.EventGrid
    ```

1. 登録が完了したことを確認してから先に進みます。

    ```bash
    az provider show --namespace Microsoft.EventGrid --query "registrationState" -o tsv
    ```

    出力に `Registered` が表示されるまで待ちます。 この実行には通常、1 から 2 分かかります。 引き続き `Registering` が表示される場合は、コマンドを再実行します。

1. Cloud Shellを閉じます。

1. ストレージ アカウント (`<storage-account-name>`) の左側のメニューで、**[セキュリティとネットワーク]** の下にある **[Microsoft Defender for Cloud] ** を選択します。

1. **[このストレージ アカウントでストレージを有効にする]** を選択します。

    > **注**: **[Microsoft Defender for Cloud]** → **[環境設定]** → お使いのサブスクリプション → **[ストレージ]** から、Defender for Storage をサブスクリプション レベルでも有効にすることができます。 サブスクリプション レベルで有効にすると、リソースごとに構成する必要がなく、サブスクリプション内の現在および将来のストレージ アカウントが自動的に保護されます。これは運用環境で推奨されるアプローチです。 ここで使用したリソース レベルでの有効化は、保護を単一のアカウントに制限し、コスト管理や選択的なカバレッジが求められる場合に役立ちます。 リソース レベルで有効にした後も、サブスクリプション レベルの **[環境設定]** ページには、Defender for Storage が **[オフ]** として表示されたままです。これは想定された状態です。 サブスクリプション プランとリソース レベルのオーバーライドは独立しています。 サブスクリプション レベルではなく、ストレージ アカウント独自の **[Microsoft Defender for Cloud]** ブレードで保護の状態を確認します。

1. 有効にした後に保護の状態が **[オン]** になることを確認します。

## 診断ログを確認する

診断ログは、ストレージ アカウントに対する管理プレーンの操作 (構成の変更、アクセス ポリシーの変更、Defender for Storage のアラートなど) をキャプチャし、保持とクエリ実行のために、それらを Log Analytics ワークスペースに転送します。

1. ストレージ アカウント (**`<storage-account-name>`**) の左側のメニューで、**[監視]** の下にある **[診断設定]** を選択します。

    このページには、ストレージ アカウントとそのサブサービスの診断設定が表示されます。 **[StorageRead]**、**[StorageWrite]**、**[StorageDelete]** は BLOB レベルのログ カテゴリであるため、BLOB のサブサービス レベルで設定を構成する必要があります。

1. リソースの一覧で、**[BLOB]** を選択します。

1. **[+ 診断設定の追加]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|

## まとめ

このラボでは、以前は脅威検知なしですべてのネットワークに開放されていた Azure ストレージ アカウントをセキュリティで保護しました。

`training-data` コンテナーに**ストアド アクセス ポリシー**を作成し、それを参照する SAS トークンを生成しました。 アカウント キーをローテーションしなければ失効させることができないスタンドアロンの SAS トークンとは異なり、ポリシーに裏付けられるトークンは、ポリシーを変更または削除すると即座に無効にできます。 ネットワーク制限が適用される前に、トークンが機能していることを確認しました。

その後、ストレージ アカウントを **[すべてのネットワークを許可する]** から VNet のみの構成に変更し、データプレーン アクセスを `sc500-lab2a-vnet` サブネットに制限し、**[Azure サービスを許可する]** 例外を削除しました。 Cloud Shell から同じ blob list コマンドを実行して 403 エラーを観察し、Azure portal のストレージ ブラウザーが現在の IP アドレスからではブロックされることも観察して、制限がアクティブであることを確認しました。

最後に、**Defender for Storage** をリソースレベルで有効にして、異常なアクセス パターンやデータ流出の試みを検出し、監査保持のために Log Analytics ワークスペースへの診断ログの転送を構成しました。
