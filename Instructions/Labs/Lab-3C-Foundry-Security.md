# AI ゲートウェイと Foundry セキュリティ コントロールを構成する

あなたの組織は、Foundry でホストされる言語モデルを API エンドポイント経由で公開していますが、現在はこのエンドポイントにレート制限もコンテンツ フィルタリングもなく、認証も要求されていません。 エンドポイントの URL を知っていれば誰でもクライアントから要求を無制限に送信でき、その中には有害なプロンプトも含まれていますが、モデルは何の制約もなく応答を返します。

セキュリティ レビューで、次の 3 つの互いに無関係なギャップが特定されました。

- **アクセス制御がない**: 匿名の呼び出し元からこのモデルに、サブスクリプション キーがなくても到達できる
- **レート制限がない**: トークンが無制限に消費され、コストの不正な増大の対策がない
- **コンテンツ安全性がない**: モデルによる有害なコンテンツの処理や生成を防ぐガードレールがない

あなたの任務は、この 3 つのギャップすべてに対処することです。 あなたはサブスクリプション キー認証とトークン レート制限を強制するための AI ゲートウェイを API Management で構成し、Prompt Shield を使用して Foundry コンテンツ安全性ガードレールを構成し、そのガードレールをデプロイ済みモデルに適用し、予防コントロールの上に検出レイヤーを追加するために AI サービス用 Defender を有効にします。

このラボでは、次のことを行います。

- 事前プロビジョニング済みの Foundry モデル エンドポイントをレビューして、セキュリティ不全状態であることを確認する
- Azure API Management で API にトークン レート制限ポリシーを適用する
- サブスクリプション キー認証を必須にして匿名アクセスを排除する
- 構成済みのゲートウェイをテストしてレート制限と認証が強制されていることを確認する
- Azure AI Foundry で Prompt Shield を使用してコンテンツ安全性ガードレールを作成してモデルに適用する
- Microsoft Defender for Cloud 内の AI サービス用 Defender を有効にする

この演習の所要時間は約 **60** 分です。

> **注**: このラボでは 2 つのポータルを使用します。[Azure portal](https://portal.azure.com) は API Management と Defender for Cloud に関して使用し、[Azure AI Foundry ポータル](https://ai.azure.com)はコンテンツ安全性ガードレールの構成に使用します。 両方のポータルを順番に使用しますが、以下の各セクションでは、各タスクにどのポータルが必要かを明示しています。

## AI ゲートウェイ トークン レート制限ポリシーを適用する

Azure API Management では、言語モデル エンドポイントに特化した AI ゲートウェイ ポリシーが用意されています。 トークン レート制限ポリシーは、呼び出し元ごとに 1 分あたりのトークン消費数を数えて上限を超えたときに HTTP 429 を返すというものであり、コストの不正な増大からエンドポイントを守ることができます。

このラボ用のポリシーの XML は、**Lab3-resources** フォルダーに用意されています。 これを APIM ポリシー エディターに直接貼り付けることができます。つまり、ポリシーの XML を記憶から書き起こす必要はありません。

1. Azure portal で、**`<apim-name>` > [API] > sc500-foundry-api** に戻ります。

1. **[デザイン]** タブを選択し、**[すべての操作]** を選択します。

1. **[受信処理]** セクションで、**</> ポリシー**のアイコンを選択してポリシー エディターを開きます。

1. 自分のラボ ファイルの中にあるファイル **Lab3-resources\sc500-lab3c-apim-policy.xml** を開きます。

1. このファイルの内容全体を選択してコピーします。

1. APIM ポリシー エディターで、既存のポリシーの内容をコピーした XML で置き換えます。

1. 保存する前に、次に示すポリシーの主要要素を確認します。

    | ポリシーの要素 | 制限の内容 |
    |----------------|-----------------|
    | `azure-openai-token-limit` | サブスクリプション キーごとに 1 分あたり 500 トークン、超過時に HTTP 429 を返す |
    | `counter-key` | 各サブスクリプション キーには独立したトークン予算が割り当てられている |
    | `estimate-prompt-tokens` | トークンのカウントはモデルが応答する前に開始し、プロンプト トークンも上限に対する使用としてカウントされる |
    | `tokens-left-header` | `x-ratelimit-remaining-tokens` 応答ヘッダーで残りの予算を呼び出し元に伝える |

1. **[保存]** を選択してポリシーを適用します。

    > **注**: この環境のコンテンツ安全性レイヤーは、APIM ポリシー レベルではなく Foundry ガードレール レベルで適用されます (このラボの、後のセクションで構成されます)。 APIM によって制限されるのは、"誰がどれくらいの頻度で呼び出せるか" であり、Foundry によって制限されるのはモデル推論レイヤーにおいて "どのコンテンツが許容されるか" です。****** 完全なセキュリティ態勢にするには、どちらのレイヤーも必要です。

## サブスクリプション キー認証を必須にする

Foundry API エンドポイントへの匿名アクセスは、最優先で対処すべきギャップです。なぜなら、レート制限が設定されていても、呼び出し元が ID なしで API セッションを無制限に作成できるとしたら効果がありません。 ここでは、サブスクリプション キーを必須とするように API を構成します。これで、APIM がキーを検証してから要求を Foundry バックエンドに転送するようになります。

1. API Management ポータルで Foundry API がまだ選択されている状態で、**[設定]** タブを選択します。

1. **[サブスクリプション]** の下の **[サブスクリプションが必要]** を **[必要]** に変更します。

1. **[サブスクリプション キー ヘッダー名]** フィールドの既定値が `Ocp-Apim-Subscription-Key` であることを確認します。これは標準的な APIM サブスクリプション キー ヘッダー名です。

1. **[保存]** を選択します。

1. 左側のメニューで **[サブスクリプション]** を選択します。

1. **[+ サブスクリプションの追加]** を選択して、次のタスクのためのテスト サブスクリプション キーを作成します。

1. サブスクリプションを次のとおりに構成します。

    | 設定 | 値 |
    |---------|-------|
    | **名前** | sc500-test-subscription |
    | **[表示名]** | SC-500 ラボ テスト キー |
    | **Scope** | API |
    | **API** | sc500-foundry-api |

1. **［作成］** を選択します

1. サブスクリプション リストにある **sc500-test-subscription** を見つけて、**[キーを表示/非表示]** を選択して主キーを表示します。 この主キーの値をコピーします。これは次のセクションで使用します。

## 構成済みのゲートウェイをテストする

トークン レート制限ポリシーとサブスクリプション キー認証が設定されたので、この両方のコントロールが期待どおりにゲートウェイによって適用されることを確認します。

1. APIM ポータルで、**[API] > [sc500-foundry-api]** に移動します。

1. **[テスト]** タブを選びます。

1. チャット完了操作 (POST エンドポイント) を選択します。

1. **[ヘッダー]** セクションで、次に示すとおりにヘッダーを追加します。

    | ヘッダー名 | ヘッダー値 |
    |-------------|-------------|
    | `Ocp-Apim-Subscription-Key` | (前のセクションでコピーしたキーを貼り付ける) |

1. **[要求本文]** セクションに、次に示すテスト プロンプトを貼り付けます。

    ```input
    {"messages": [{"role": "user", "content": "What is the capital of France?"}], "max_tokens": 50}
    ```

1. **[送信]** を選択し、**HTTP 200** とモデルからの応答が返されることを確認します。これは、有効なサブスクリプション キーを使用して要求に成功したことを示します。

1. `Ocp-Apim-Subscription-Key` ヘッダーをテスト パネルから削除します (または値をクリアします)。

1. もう一度 **[送信]** を選択し、**HTTP 401 Unauthorized** が返されることを確認します。これは、サブスクリプション キーがなく要求が拒否されたことを示します。

1. レート制限の振る舞いを確認するために、Azure Cloud Shell を使用してサブスクリプション キーを指定した要求を短時間で立て続けに送ります。

    1. **Cloud Shell** を Azure portal のツール バーから開きます (`>_` アイコン)。

    1. Cloud Shell プロンプトで、次に示すコマンドを実行します。`<your-key>` を自分のサブスクリプション キーで置き換え、`<your-apim-gateway-url>` を自分の APIM ゲートウェイ URL で置き換えてください (`<apim-name>` の概要ページの**ゲートウェイ URL** の下に表示されます)。

        ```bash
        for i in {1..10}; do curl -s -o /dev/null -w "%{http_code}\n" -X POST "https://<your-apim-gateway-url>/sc500-foundry-api/chat/completions?api-version=2024-02-01" -H "Ocp-Apim-Subscription-Key: <your-key>" -H "Content-Type: application/json" -d '{"messages":[{"role":"user","content":"Summarize the security risks of unprotected AI endpoints in 100 words."}],"max_tokens":100}'; done
        ```

    1. 返される HTTP 状態コードを観察します。 最初の数件の要求に対しては **200** が返されます。 1 分あたり 500 トークンという上限に達すると、それ以降の要求に対して **429 Too Many Requests** が返されます。つまり、レート制限ポリシーが適用されてトークン予算が守られています。

    > **注**: 何回目の要求で 429 という応答が返されるかについて、正確な数は各応答のトークン数によって決まります。 `max_tokens` が 100 に設定され、1 分あたりのトークン数が 500 と構成されている場合は、一般的に 5 番目か 6 番目の要求までに制限に達します。 レート制限カウンターは 1 分後にリセットされます。

## コンテンツ安全性ガードレールを Azure AI Foundry 内に作成する

コンテンツ安全性ガードレールは Foundry レイヤーで適用されます。その機能は、モデルに送られたプロンプトとモデルの応答の両方を検査して、構成済みの有害性しきい値を越えるコンテンツをブロックすることです。 ここでは、Prompt Shield を有効にしたガードレールを作成し、gpt-4o-mini デプロイに適用します。

1. **Azure AI Foundry ポータル**のタブに戻ります (または [https://ai.azure.com](https://ai.azure.com) に移動します)。

1. **sc500-lab3c-foundry** プロジェクトを選択します。

1. 左側のナビゲーションの **[安全性とセキュリティ]** の下の **[コンテンツ フィルター]** を選択します。

1. **[+ コンテンツ フィルターの作成]** を選択します。

1. **[基本情報]** ステップで、次のとおりに構成します。

    | 設定 | Value |
    |---------|-------|
    | **フィルター名** | sc500-safety-filter |

1. **[次へ]** を選択して入力フィルターの構成に進みます。

1. **[入力フィルター]** ステップで、**プロンプト入力** (ユーザーからモデルに送られるもの) の 4 つの有害性カテゴリすべてのしきい値を構成します。

    | カテゴリ | しきい値 |
    |----------|-----------|
    | **ヘイトと公平性** | Medium |
    | **暴力** | Medium |
    | **性的** | Medium |
    | **自傷行為** | Medium |

    > **注**: しきい値が **[中]** のときは、プロンプトがモデルに転送される前に、コンテンツのうち明らかに有害なものがガードレールによってブロックされます。 **[低]** のときはさらに厳格になり (ボーダーラインのコンテンツがブロックされる)、**[高]** のときは極端なコンテンツのみがブロックされます。 ほとんどの本番デプロイについては、最初は "中" とすることが推奨されます。

1. **[次へ]** を選択して出力フィルターの構成に進みます。

1. **[出力フィルター]** ステップで、同じしきい値 "中" を**完了出力** (モデルから呼び出し元に返されるもの) の 4 つの有害カテゴリすべてに対して構成します。

    | カテゴリ | しきい値 |
    |----------|-----------|
    | **ヘイトと公平性** | Medium |
    | **暴力** | Medium |
    | **性的** | Medium |
    | **自傷行為** | Medium |

1. **[次へ]** を選択して Prompt Shield ステップに進みます。

1. **[Prompt Shield]** ステップで、次のとおりに **Prompt Shield** を有効にします。

    - **脱獄検知**: **[オン]** に設定します。これで、モデルのシステム指示を無視しようとするプロンプトがブロックされます。
    - **間接攻撃検知**: **[オン]** に設定します。これで、モデルに渡されるドキュメントまたはコンテキストに埋め込まれるプロンプト インジェクションの試みがブロックされます。

1. **[次へ]** を選択し、構成の要約を確認してから **[作成]** を選択します。

### ガードレールをモデル デプロイに適用する

1. 左側のナビゲーションで **[モデル + エンドポイント]** (または **[デプロイ]**) を選択します。

1. **gpt-4o-mini** デプロイを選択します。

1. **[編集]** または **[デプロイの設定を更新]** を選択します。

1. **[コンテンツ フィルター]** フィールドで、**sc500-safety-filter** をドロップダウンから選択します。

1. **[更新]** (または **[保存]**) を選択してガードレールをデプロイに適用します。

1. **[安全性とセキュリティ] > [コンテンツ フィルター]** に戻り、**sc500-safety-filter** のところに割り当て済みデプロイとして **gpt-4o-mini** が表示されていることを確認します。

    > **注**: これでガードレールがアクティブになりました。 gpt-4o-mini エンドポイントに対する要求のうち、そのコンテンツが "中" しきい値を超えるもの、または脱獄を試みるものは、モデルがプロンプトを処理する前に Foundry レイヤーにおいてブロックされます。 ガードレールを通過した要求も、前に構成した APIM トークン レート制限とサブスクリプション キー要件の対象となります。 この 2 つのレイヤーは独立して作用し、どちらも必須です。

## AI サービス用 Defender を有効にする

APIM ゲートウェイと Foundry ガードレールは**予防的**コントロールであり、有害な要求をブロックします。 AI サービス用 Defender は**検出**のためのコントロールです。つまり、AI ワークロードの振る舞いパターンを経時的に監視し、攻撃シーケンスが検出されたときにアラートを発します。これは、個々の要求がブロックされているときでも行われます。

1. **Azure portal** のタブに戻ります。

1. 検索バーで **Microsoft Defender for Cloud** を検索して選択します。

1. 左側のメニューで **[環境設定]** を選択します。

1. 一覧からご利用のサブスクリプションを選択します。

1. **[Defender プラン]** ページで、スクロールして **[AI サービス]** (または **[Defender for AI]**) を見つけます。

1. **[AI サービス]** プランを **[オン]** に設定します。

1. ページの最上部で **[保存]** を選択します。

1. 左側のメニューで **[ワークロード保護]** を選択します。

1. **[AI]** セクションまでスクロールして、**sc500-lab3c-foundry** が対象リソースとして表示されていることを確認します。

## セキュリティ アーキテクチャをレビューする

本日構成した 3 つのコントロールは、次のように AI エンドポイント セキュリティのそれぞれ異なる面に対処するものです。

| コントロール レイヤー | Type | 対処の対象 |
|---------------|------|------------------|
| **APIM サブスクリプション キー** | 予防的 - アクセス制御 | 匿名の呼び出し元をブロックする (どの要求も有効なキーを提示する必要がある) |
| **APIM トークン レート制限** | 予防的 - 量の制御 | キーごとの 1 分あたりの消費量を制限し、コストの不正な増大から守る |
| **Foundry コンテンツ安全性 + Prompt Shield** | 予防的 - コンテンツ制御 | モデル処理前に有害なプロンプトや脱獄の試みをブロックする |
| **AI サービス用 Defender** | 検出 - 振る舞い監視 | 複数の要求にわたる攻撃キャンペーンを特定する、SOC 調査のためのセキュリティ アラートを生成する |

単一の予防的レイヤーだけでは不十分です。 攻撃者はサブスクリプション キーを入手すれば脱獄を試行できてしまいます。 攻撃者は個々の要求でガードレールによってブロックされても、多数のセッションにわたる脱獄キャンペーンを実行できます。 AI 用 Defender はそのようなキャンペーン パターンを検出してユーザー組織の SOC にアラートを送りますが、これは個々の要求がブロックされた場合でも行われます。 完全なセキュリティ態勢を作るには、4 つのコントロールすべてが必要です。

## まとめ

このラボでは、Foundry でホストされる AI エンドポイントに存在する、3 つの互いに無関係なセキュリティ ギャップを修復しました。 Azure API Management で、トークン レート制限ポリシーを適用して 1 分あたり 500 トークンという消費制限を適用するとともにサブスクリプション キー認証を必須にし、これで匿名アクセスを排除しました。 両方のコントロールのテストを、APIM テスト コンソールと Cloud Shell を使用して行いました。

Azure AI Foundry で、コンテンツ安全性ガードレールを **sc500-safety-filter** という名前で作成し、有害性しきい値を 4 つの有害性カテゴリすべてに対して "中" に設定するとともに、Prompt Shield を有効にして脱獄と間接攻撃の両方を検出できるようにしました。 このガードレールを gpt-4o-mini デプロイに適用しました。

Microsoft Defender for Cloud で、AI サービス用 Defender をサブスクリプションに対して有効にし、これで振る舞い検出レイヤーを予防コントロールの上に追加しました。

この演習は無事に完了しました。

## クリーンアップ

ラボ環境は、セッション終了時に自動的にリセットされます。 手動でリソースを削除する必要はありません。

セッション終了前にコンテンツ安全性ガードレールをモデル デプロイから除去する手順は次のとおりです。

1. Azure AI Foundry ポータル > **sc500-lab3c-foundry** > **[モデル + エンドポイント]** に移動します。
1. **gpt-4o-mini** デプロイを選択してデプロイ設定の編集画面に移動します。
1. **[コンテンツ フィルター]** を既定のフィルターに戻すか、なしに設定してから保存します。
