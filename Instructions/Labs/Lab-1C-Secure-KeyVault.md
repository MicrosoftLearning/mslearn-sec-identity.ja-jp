# Azure Key Vault をデプロイしてセキュリティで保護する

組織の AI プラットフォームの最近のセキュリティ レビューでは、Azure AI Foundry 統合でモデル エンドポイントに対する認証に使用される API キーを含むアプリケーション シークレットが、アプリケーション構成ファイル内にプレーン テキストで格納されていることがわかりました。 デプロイ構成またはソース リポジトリにアクセスできるすべてのユーザーがこれを読み取ることができます。 あなたのタスクは、これらのシークレットを Azure Key Vault に移行し、アプリケーションのマネージド ID のみがそれらを取得できるようにアクセスを制限し、Defender for Key Vault による資格情報コンテナーの保護を確保することです。

Azure Key Vault は、シークレット、暗号化キー、証明書用に、一元管理されたハードウェアで保護されたストアを提供します。 マネージド ID と組み合わせると、アプリケーションは資格情報を処理することなく Key Vault に対して認証します。プラットフォームは Azure Instance Metadata Service (IMDS) を介してトークンの取得を自動的に処理し、アクセスは Azure RBAC の役割の割り当てで管理されます。 ネットワーク ファイアウォールを追加すると、2 つ目の強制レイヤーが作成され、承認されていないネットワークからは、有効な ID でも資格情報コンテナーに到達できなくなります。

このラボでは、次のことを行います。

- Azure RBAC 認可モデルを使用して Azure Key Vault をデプロイする
- アプリケーションのマネージド ID とテスト ユーザー アカウントにロールベースのアクセスを割り当てる
- 資格情報コンテナーに API キーと暗号化キーを保管する
- 制限された閲覧者ロールがシークレット値へのアクセス権を与えていないことを確認する
- マネージド ID トークン エンドポイントを通じて、App Service のマネージド ID を使ってシークレットを取得する
- 資格情報コンテナー ネットワークへのアクセスを認可された仮想ネットワークに制限する
- Defender for Key Vault 保護計画を有効にし、監査ログの転送を構成する

この演習の所要時間は約 **60** 分です。

> **注**: このラボでは、**User1** アカウント (主要なラボの資格情報と管理者) と **User2** (データ プレーンでロールベースのアクセス境界が適用されていることの確認に使用) の 2 つのアカウントを使用します。 両方のアカウントに指定した認証情報を使用してください。

## Key Vault をデプロイする

Azure Key Vault は、**資格情報コンテナー アクセス ポリシー** (レガシーモデル) と **Azure ロールベースのアクセス制御** (推奨モデル) という 2 つの権限モデルをサポートしています。 RBAC モデルでは、Key Vault のアクセス ガバナンスが、すべての Azure リソースで使用されるのと同じロール割り当てシステムに統合されるため、アクセス許可を監査し、最小限の特権の原則を一貫して適用することが容易になります。 RBAC モデルを有効にして資格情報コンテナーを作成し、その削除保護設定を確認して構成します。

> **注**: Key Vault 名は、すべての Azure サブスクリプションでグローバルに一意であることが必要です。 次のステップでは、**`sc500-kv-`** で始まる自分の名前 (たとえば、`sc500-kv-yourinitials-1234`) を選択します。 このラボの残りの部分では、`<your-kv-name>` は、ここで入力した名前を参照します。後のセクションで再利用するため、その名前を書き留めるか、メモ帳ウィンドウを開いたままにしておきます。

1. **User1** の資格情報を使用して **Azure portal** (`https://portal.azure.com`) にサインインします。

2. 検索バーで、**キー コンテナー**を検索して選択します。

3. **[+ 作成]** を選択します。

4. **[基本]** タブで次の値を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **サブスクリプション** | ラボのサブスクリプション |
    | **リソース グループ** | sc500-lab1c-rg |
    | **キー コンテナー名** | `sc500-kv-` で始まるグローバルに一意の名前 (たとえば、`sc500-kv-yourinitials-1234`)。 後の手順で使用するために `<your-kv-name>` として記録しておきます。 |
    | **リージョン** | ラボ セットアップ時に選択した Azure リージョン (ラボ環境で特に指示されない限り、米国東部) を使用します |
    | **価格レベル** | Standard |

5. **[アクセスの構成]** タブを選択します。

6. **[アクセス許可モデル]** で、**[Azure ロールベースのアクセス制御 (RBAC)]** を選択します。

    > **注**: RBAC 認可モデルは資格情報コンテナーの作成時に選択され、資格情報コンテナーを削除して再作成しないと変更できません。 レガシ アクセス ポリシー モデルを使用して資格情報コンテナーを作成した場合、このラボのロールの割り当ての手順は適用されません。

7. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

    デプロイが完了するまで待ちます。 通常、所要時間は 1 分以下です。

8. **[リソースに移動]** を選択して資格情報コンテナーを開きます。

9. Key Vault の **[概要]** ページで、**[Vault URI]** フィールドを見つけます。 この値をコピーして保存します。形式は `https://<your-kv-name>.vault.azure.net/` です。 これは後のセクションで使用します。 Windows のメモ帳は、この情報を保存するのに適したツールです。

10. 左側のメニューの **[設定]** で、**[プロパティ]** を選択します。

11. **[論理的な削除]** を見つけて、**[この資格情報コンテナーでは、論理的な削除が有効です]** と表示されていることを確認します。

    > **注**: 論理的な削除は新しい Key Vault インスタンスのすべてで既定で有効化されており、一度設定されると無効化できません。 これは、削除されたシークレット、鍵、証明書を設定可能な保持期間中 (既定値: 90 日)、回復可能な状態に保持し、誤ったまたは悪意のある削除から守ります。

12. **[消去保護]** を見つけて、**[無効]** と表示されていることを確認します。

13. **[消去保護を有効にする]** を選択し、**[保存]** を選択します。

    > **注**: パージ保護は、論理的な削除期間中に、Key Vault 投稿者ロールを持つユーザーによるものであっても、資格情報コンテナーやそのオブジェクトの永久削除を防ぎます。 これは一方向の操作であり、一度有効化されると元に戻すことはできません。 運用環境では、重要なシークレットまたはキーを格納するすべての資格情報コンテナーに対して消去保護を設定することをおすすめします。

## Azure RBAC を使用してアクセス権を設定する

資格情報コンテナーが作成されたら、最小限の特権の原則に従って 4 つの RBAC の役割を割り当てます。 **User1** の管理者アカウントに広範な管理者ロールを付与するのではなく、**Key Vault シークレット責任者** (シークレットの作成と管理) と **Key Vault 暗号化責任者** (キーの作成と管理) という 2 つの対象となるロールを割り当てます。 その後、**Key Vault シークレット ユーザー** ロールを App Service マネージド ID (実行時にシークレットを取得する) に付与し、**Key Vault Reader** ロールを **User2** (管理プレーン アクセスがデータプレーンにシークレット値へのアクセスを付与しないことを検証するために使用する) に付与します。

> **注**: Key Vault が RBAC 認可モデルを使用する場合、データプレーン アクセスは、資格情報コンテナーを作成したアカウントを含めた役割の割り当てによって完全に制御されます。 サブスクリプションの所有者ロールとグローバル管理者ロールは、Key Vault に対するデータプレーン権限を付与しません。 明示的な割り当てがなければ、管理者アカウントはシークレットや鍵の作成、読み取り、削除ができません。

`sc500-lab1c-app` App Service には、ラボの開始前に事前に有効化されているシステム割り当てマネージド ID があります。 App Service 自体の設定は不要で、この資格情報コンテナーへのアクセスを ID に付与するだけで十分です。

1. Key Vault の左側のメニューで **[アクセス制御 (IAM)]** を選択します。

1. **[+ 追加]** を選択し、**[ロールの割り当ての追加]** を選択します。

1. **[役割]** タブで、**Key Vault シークレット責任者**を検索して選択し、**[次へ]** を選択します。

    > **注**: **Key Vault シークレット責任者** の役割は、シークレットの作成、読み取り、更新、削除、削除権限のみを付与し、鍵や証明書へのアクセスは含みません。 これを **Key Vault 暗号化責任者**と別に割り当てることが分離を強化します。シークレット責任者のみのアカウントは鍵を管理できず、その逆も同様です。

1. **[メンバー]** タブで、**[アクセスの割り当て先]** が **[ユーザー、グループ、またはサービス プリンシパル]** に設定されていることを確認します。

1. **[+ メンバーを選択する]** を選択し、**User1** アカウント (現在サインインに使用しているアカウント) を検索して選択し、**[選択]** を選択します。

1. **[レビューと割り当て]** を選択し、もう一度 **[レビューと割り当て]** を選択して保存します。

1. **[+ 追加]** を選択し、**[ロールの割り当ての追加]** を選択して、2 番目の割り当てを開始します。

1. **[役割]** タブで、**Key Vault 暗号化責任者**を検索して選択し、**[次へ]** を選択します。

    > **注**: **Key Vault 暗号化責任者** の役割は、鍵の作成、読み取り、更新、削除、消去の権限のみを付与します。 キー管理とシークレット管理を分離することは、ゼロ トラスト設計原則です。暗号化キーを管理するユーザーまたはプロセスが自動的にアプリケーション シークレットを読み取ることができるわけではありません。

1. **[メンバー]** タブで、**[アクセスの割り当て先]** が **[ユーザー、グループ、またはサービス プリンシパル]** に設定されていることを確認します。

1. **[+ メンバーを選択する]** を選択し、**User1** アカウント (現在サインインに使用しているアカウント) を検索して選択し、**[選択]** を選択します。

1. **[レビューと割り当て]** を選択し、もう一度 **[レビューと割り当て]** を選択して保存します。

1. **[+ 追加]** を選択し、**[ロールの割り当ての追加]** を選択して、3 番目の割り当てを開始します。

1. **[役割]** タブで、**Key Vault シークレット ユーザー**を検索して選択し、**[次へ]** を選択します。

    > **注**: **Key Vault シークレット ユーザー**の役割は、シークレットのコンテンツに対する読み取りアクセスのみを付与します。これは、アプリケーションが実行時にシークレット値を取得できるだけの権限です。 シークレットの作成、更新、一覧表示、または削除は許可されません。 これは、アプリケーションのマネージド ID がシークレットを読み取るために必要な最小限の権限です。

1. **[メンバー]** タブの **[アクセス権の割り当て先]** で、**[マネージド ID]** を選択します。

1. **[+ メンバーを選択する]** を選択します。

1. **[マネージド ID の選択]** ペインで、**[マネージド ID]** を **[App Service]** に設定し、リストから **[sc500-lab1c-app]** を選択します。

1. **[選択]** を選択し、**[レビューと割り当て]** を選択し、もう一度 **[レビューと割り当て]** を選択して保存します。

1. **[+ 追加]** を選択し、**[ロールの割り当ての追加]** を選択して、4 番目の割り当てを開始します。

1. **[役割]** タブで、**Key Vault 閲覧者**を検索して選択し、**[次へ]** を選択します。

    > **注**: **Key Vault 閲覧者** ロールは、Key Vault メタデータ (資格情報コンテナーのプロパティ、シークレットの名前と鍵の名前) への読み取りアクセス権を付与しますが、シークレット値やキー マテリアルを表示するアクセス許可は付与しません。 これは管理プレーンのみのロールです。 この境界線は次のセクションで確認します。

1. **[メンバー]** タブで、**[アクセスの割り当て先]** を **[ユーザー、グループ、またはサービス プリンシパル]** に設定します。

1. **[+ メンバーの選択]** を選択し、「**User2**」を検索して選択し、**[選択]** を選択します。

1. **[レビューと割り当て]** を選択し、もう一度 **[レビューと割り当て]** を選択して保存します。

1. **[アクセス制御 (IAM)]** ページで **[ロールの割り当て]** タブを選択し、次の 4 つの割り当てが一覧表示されていることを確認します。

    | プリンシパル | 役割 |
    |-----------|------|
    | ユーザー 1 | キー コンテナー シークレット責任者 |
    | ユーザー 1 | Key Vault 暗号化担当者 |
    | sc500-lab1c-app | キー コンテナー シークレット ユーザー |
    | ユーザー 2 | キー コンテナー閲覧者 |

    > **注**: 運用環境では、**Key Vault シークレット責任者**と **Key Vault 暗号化責任者**の割り当てをアクティブにするのではなく、Privileged Identity Management (PIM) を通じて適格にすることを検討してください。 これにより、常時有効になっているデータプレーンへのアクセスは完全に削除されます。管理者は、資格情報コンテナーの内容の管理が必要な場合に、ジャストインタイムでロールをアクティブ化し、アクセス権は自動的に期限切れになります。

## シークレットと鍵を保存する

次に、AI アプリケーションのモデル エンドポイント API キーを表すシークレットと、Key Vault を介して管理されるデータ暗号化キーを表す暗号化キーという 2 つのオブジェクトを資格情報コンテナーに格納します。 これらのオブジェクトは、その後のアクセス検証およびマネージド ID 取得のステップで使用されます。

1. Key Vault の左側のメニューで、**[オブジェクト]**、**[シークレット]** の順に選択します。

1. **[生成/インポート]** を選択します。

1. **[シークレットの作成]** ページで、次を設定します。

    | 設定 | 値 |
    |---------|-------|
    | **Upload options** | 手動 |
    | **名前** | `foundry-api-key` |
    | **シークレット値** | `sk-foundry-demo-00000000000000000000000000000001` |
    | **Enabled** | はい |

1. **［作成］** を選択します

    シークレットはシークレット リストに **[有効]** の状態で表示されます。

1. 左側のメニューで、**[キー]** を選択します。

1. **[生成/インポート]** を選択します。

1. **[キーの作成]** ページで、次を設定します。

    | 設定 | 値 |
    |---------|-------|
    | **[オプション]** | 作成 |
    | **名前** | `data-encryption-key` |
    | **キー**型 | RSA |
    | **RSA キー サイズ** | 2048 |
    | **Enabled** | はい |

1. **［作成］** を選択します

    キーはキー リストに **[有効]** の状態で表示されます。

    > **注**: Key Vault では、RSA 秘密キー マテリアルが資格情報コンテナー内に格納されており、直接公開されることはありません。 アプリケーションは生の鍵を抽出するのではなく、鍵の暗号化操作 (暗号化、暗号化の解除、署名、検証) を呼び出して鍵とやり取りします。 これにより秘密鍵は資格情報コンテナー内で永続的に保護され、監査されます。

## アクセス制御の適用を確認する

**Key Vault 閲覧者**ロールは管理プレーンへのアクセスのみを付与します。この役割を割り当てられたユーザーはシークレットの存在を確認し、その名前を見ることはできますが、シークレットの値は読み取れません。 あなたは、**User2** としてサインインして、ロールの境界がデータ プレーンに適用されていることを確認します。

1. **InPrivate** または**プライベート**の新しいブラウザー ウィンドウを開きます。

1. Azure portal (`https://portal.azure.com`) に移動し、**User2** に指定した認証情報を使用してサインインします。

1. 検索バーで、**キー コンテナー**を検索して選択します。

1. リストから **`<your-kv-name>`** を選択します。

1. 左側のメニューで **[オブジェクト]** を開き、**[シークレット]** を選択します。

    **foundry-api-key** がリストに表示されていることを確認します。 Key Vault 閲覧者の役割により **User2** 管理プレーンへのアクセスが付与されるため、シークレット名が表示されています。

1. **[foundry-api-key]** を選択してシークレットを開き、現在のバージョンを選択します。

1. シークレット バージョンのページで **[シークレット値を表示]** を選択します。

    **"この操作は RBAC で許可されていません。ロールの割り当てが最近変更された場合は、ロールの割り当てが有効になるまで数分お待ちください。"** という内容のエラー メッセージが表示されることを確認します。 または、アクセス拒否の通知が表示されます。

    > **注**: Key Vault 閲覧者ロールには `Microsoft.KeyVault/vaults/read` (管理プレーン) が含まれますが、`Microsoft.KeyVault/vaults/secrets/getSecret/action` (データ プレーン) は含まれません。 つまり、**User2** はシークレットを列挙することはできますが、その値を取得することはできません。これが閲覧者の役割とシークレット ユーザーの役割を隔てる境界です。

1. InPrivate ブラウザー ウィンドウを閉じて、User1 のブラウザーのセッションに戻ります。

## マネージド ID を使ってシークレットを取得する

`sc500-lab1c-app` App Service マネージド ID には、データプレーンから秘密値へのアクセスを許可する **Key Vault シークレット ユーザー**ロールを持っています。 このアプリは Linux 上で動作するため、コンテナーに SSH セッションを開き、マネージド ID に発行されたベアラー トークンを使って `foundry-api-key` シークレットを取得します。 この取得には、ユーザー資格情報は関与しません。

マネージド ID が App Service で有効になっている場合、ランタイムは、`IDENTITY_ENDPOINT` (ローカル トークン サービス URL) と `IDENTITY_HEADER` (SSRF 攻撃を防ぐ共有シークレット) という 2 つの環境変数をアプリケーションのプロセスに挿入します。 App Service 内で実行されているコードは、これらを使用して、ID にアクセス権が付与されている Azure リソースにスコープを指定した OAuth トークンを要求します。

> **注**: マネージド ID には、**Basic (B1) レベル** App Service 以上が必要です。 Free(F1) レベルはマネージド ID をサポートしていません。 セットアップ テンプレートはこのアプリを B1 にデプロイします。

1. **User1** アカウントとして Azure portal (`https://portal.azure.com`) にサインインしていることを確認します。 前のセクションの InPrivate ウィンドウがまだ有効であれば、まずそれを閉じます。

1. Azure portal の上部バーで、**Cloud Shell** アイコン (>_) を選択します。 シェルの種類を選択するように求められたら、**[Bash]** を選択します。

1. Linux App Service コンテナーで SSH セッションを開くには、次のコマンドを実行します。

    ```bash
    az webapp ssh --resource-group sc500-lab1c-rg --name sc500-lab1c-app
    ```

    プロンプトが変更され、コマンドが App Service コンテナー内で実行されていることが示されるまで待ちます。

1. マネージド ID 環境変数が存在することを確認するために、次のコマンドを実行します。

    ```bash
    printf 'IDENTITY_ENDPOINT: %s\n' "$IDENTITY_ENDPOINT"
    if [ -n "$IDENTITY_HEADER" ]; then
      echo 'IDENTITY_HEADER is set: True'
    else
      echo 'IDENTITY_HEADER is set: False'
    fi
    ```

    想定される出力:

    ```text
    IDENTITY_ENDPOINT: http://127.0.0.1:<port>/MSI/token
    IDENTITY_HEADER is set: True
    ```

    > **重要**: `IDENTITY_ENDPOINT` が空欄、または `IDENTITY_HEADER is set: False` の場合は、SSH セッションを終了してください。 **sc500-lab1c-app > [設定]> [ID]** の順に移動し、**[システム割り当て]** の状態が **[オン]** であることを確認します。 また、App Service プランが **Basic (B1)** レベル以上を使っていることも確認します。

1. 次のコマンドを実行して Azure Key Vault のベアラー トークンを要求し、コンテナーに既にインストールされている Node.js ランタイムでそれを抽出します。

    ```bash
    token_response=$(curl --silent --show-error --fail \
      "${IDENTITY_ENDPOINT}?resource=https%3A%2F%2Fvault.azure.net&api-version=2019-08-01" \
      -H "X-IDENTITY-HEADER: ${IDENTITY_HEADER}")

    token=$(printf '%s' "$token_response" | node -e \
      'let input=""; process.stdin.on("data", c => input += c); process.stdin.on("end", () => process.stdout.write(JSON.parse(input).access_token));')

    echo "Token acquired: ${token:0:20}..."
    ```

    トークン値の一部で、マネージド ID が有効なトークンを返したことが確認できます。

    > **注**: App Services では、仮想マシンの IMDS アドレス (`169.254.169.254`) ではなくローカル トークン エンドポイントが使用されます。 `X-IDENTITY-HEADER` 値は、承認されていないプロセスがそのエンドポイントを介してトークンを要求することを防ぎます。

1. 次のコマンドを実行します。 `<your-kv-name>` を、先ほど記録した Key Vault 名に置き換えます。

    ```bash
    kv_uri="https://<your-kv-name>.vault.azure.net"
    secret_response=$(curl --silent --show-error --fail \
      "${kv_uri}/secrets/foundry-api-key?api-version=7.4" \
      -H "Authorization: Bearer ${token}")

    secret_value=$(printf '%s' "$secret_response" | node -e \
      'let input=""; process.stdin.on("data", c => input += c); process.stdin.on("end", () => process.stdout.write(JSON.parse(input).value));')

    echo "Secret value: ${secret_value}"
    ```

    出力には、先ほど保存したシークレット値が表示されます。

    ```text
    Secret value: sk-foundry-demo-00000000000000000000000000000001
    ```

    > **注**: ベアラー トークンは Key Vault に対する `sc500-lab1c-app` マネージド ID を識別します。 Key Vault では値を返す前に、その ID が **Key Vault シークレット ユーザー**の役割を持っていることが確認されます。

1. `exit` を実行して App Service SSH セッションを閉じてから、Cloud Shell を閉じます。

## ネットワーク アクセスを制限する

ID ベースのアクセス制御は Key Vault の主要な強制メカニズムです。 ネットワーク ファイアウォールは、ロールの割り当てに関係なく、資格情報コンテナーのデータ プレーンにアクセスできるネットワークを制限して、第二の防御層を追加します。 Key Vault ファイアウォールは、`sc500-lab1c-vnet` 仮想ネットワークからのアクセスのみを許可するように設定します。

> **注**: `sc500-lab1c-vnet` 仮想ネットワークは、`Microsoft.KeyVault` サービス エンドポイントがそのサブネット上で既に有効化された状態で、事前プロビジョニングされていました。 VNet を Key Vault のファイアウォール許可リストに追加するには事前に行う必要があります。サービス エンドポイントはサブネットを設定し、Key Vault トラフィックを、パブリック インターネット経由ではなく、Azure のバックボーン経由で直接ルーティングするように設定します。

1. Key Vault **`<your-kv-name>`** に移動します。

1. 左側のメニューの **[設定]** で、**[ネットワーク]** を選択します。

1. **[許可するアクセス元]** で、**[特定の仮想ネットワークと IP アドレスからのパブリック アクセスを許可する]** を選択します。

1. **[仮想ネットワーク]** で、ドロップダウンを使用して **[+ 既存の仮想ネットワークの追加]** を選択します。

1. **[ネットワークの追加]** ペインで、次の値を設定します。

    | 設定 | 値 |
    |---------|-------|
    | **サブスクリプション** | ラボのサブスクリプション |
    | **仮想ネットワーク** | sc500-lab1c-vnet |
    | **サブネット** | 利用可能なサブネットを選択します - 既定値 |

1. **[追加]** を選択します。

1. **[例外]** で、**[信頼できる Microsoft サービスがこのファイアウォールをバイパスすることを許可します]** が選択されていることを確認します。

    > **注**: 信頼できる Microsoft サービス例外により、Azure Monitor、Azure Backup、Azure Defender などの Azure プラットフォーム サービスは、ファイアウォールで他のすべてのトラフィックが制限されていても、監視や保護のために資格情報コンテナーにアクセスできます。

1. **[適用]** を選択してファイアウォール構成を保存します。

    > **注**: 保存後、資格情報コンテナーは `sc500-lab1c-vnet` サブネットおよび信頼できるサービス リストの Azure サービスからのデータプレーン トラフィックのみを受け入れます。 Azure portal に、"お使いの現在の IP は、許可リストに含まれていません" という内容のバナー警告が表示されることがありますが、これは想定されている動作です。 このステップの後にポータルから資格情報コンテナーにアクセスする必要がある場合は、ラボ環境のパブリック IP をファイアウォールの **IP アドレス** セクションに一時的に追加するか、`sc500-lab1c-vnet` と VNet 統合された Azure リソースを使うことができます。

## Defender for Key Vault を有効にする

Microsoft Defender for Key Vault は、既知の悪意のある IP アドレスからのアクセス、疑わしい取得ボリューム、異常な地理的位置など、異常で潜在的に有害なアクセス パターンを検出します。 サブスクリプションで Defender for Key Vault 保護計画を有効にし、監査ログを事前プロビジョニング済みの Log Analytics ワークスペースに転送するよう資格情報コンテナーを構成します。

1. Azure portal の検索バーで、「`https://portal.azure.com`」を検索して **`Microsoft Defender for Cloud`** を選択します。

1. 左側のメニューの **[管理]** で、**[環境設定]** を選択します。  ページの一番下までスクロールします。

1. **[すべてを展開]** ボタンを使用してサブスクリプション ノードを展開し、ご自分のサブスクリプションを選択します。

1. **[Defender プラン]** ページの、リソースの種類の一覧で **Key Vault** を見つけます。

1. **[Key Vault]** プランの状態を **[オン]** に設定します。

1. **[保存]** を選択します。

    > **注**: Defender for Key Vault を有効にすると、このラボで作成した資格情報コンテナーを含む、サブスクリプション内のすべての Key Vault で脅威検出がアクティブになります。 アラートは、Tor の終了ノードからのアクセス、特殊な地理的な場所からのアクセス、資格情報の収集の試行を示す可能性がある一括シークレット取得パターンなどの異常に対して生成されます。

1. Key Vault (**`<your-kv-name>`**) に戻ります。

1. 左側のメニューの **[監視]** で、**[診断設定]** を選択します。

1. **[+ 診断設定の追加]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **診断設定の名前** | `sc500-kv-diag` |
    | **ログ - カテゴリ グループ** | **[監査]** にチェックを入れる |
    | **宛先の詳細** | **[Log Analytics ワークスペースへの送信]** にチェックを入れる |
    | **サブスクリプション** | ラボのサブスクリプション |
    | **Log Analytics ワークスペース** | sc500-lab1c-log |

1. **[保存]** を選択します。

1. **sc500-kv-diag** が診断設定リストに表示されたことを確認します。

    > **注**: 診断設定では、すべての Key Vault 監査イベント (シークレット、キー、証明書の読み取り、書き込み、削除の操作) が Log Analytics ワークスペースに転送されます。 このテレメトリは Defender for Key Vault のアラート強化に反映され、セキュリティ調査やコンプライアンス報告を支援します。 設定の保存後、最初のログ エントリがワークスペースに表示されるまで最大 15 分ほどかかります。

## まとめ

このラボでは、Azure Key Vault をエンドツーエンドでセキュリティにより保護しました。 RBAC 認可モデルを使用してコンテナーをデプロイし、アクセス ガバナンスがすべての Azure リソースで使用されるのと同じロール割り当てシステムと統合されるようにしました。 App Service のマネージド ID に必要最小限の権限 (**Key Vault シークレット ユーザー**) 付与し、**User2** に割り当てられた **Key Vault 閲覧者**の役割が管理プレーンとデータプレーンの境界を強制し、ユーザーはシークレットの存在は確認できますが、その値は読み取れないことを確認しました。 シミュレーションされた AI アプリケーション API キーと暗号化キーを保存し、App Service マネージド ID エンドポイントから取得したマネージド ID ベアラー トークンを使って App Service からプログラムでシークレットを取得しました。どの段階にも、保存されている資格情報は関与していません。 最後に、認可された仮想ネットワークへの資格情報コンテナー アクセスを制限するネットワーク ファイアウォールを適用し、Defender for Key Vault 保護計画を有効にし、Log Analytics ワークスペースへの監査ログ転送を構成しました。

この演習は無事に完了しました。

## クリーンアップ

ラボ環境は、セッション終了時に自動的にリセットされます。 手動でリソースを削除する必要はありません。

セッションが終了する前にクリーンアップする場合:

1. [Azure Portal](https://portal.azure.com) に移動します。
1. **[リソース グループ]** に移動し、**sc500-lab1c-rg** を選択します。
1. **[リソース グループの削除]** を選び、リソース グループの名前を入力して確認し **[削除]** を選択します。
1. **[Microsoft Defender for Cloud]** → **[管理]** → **[環境設定]** で、お使いのサブスクリプションを選択し、**[Key Vault]** プランを **[オフ]** に設定し、**[保存]** を選択します。
