# ネットワーク セキュリティ制御を構成する

AI 推論ワークロードの侵入テストで、クリティカルなネットワーク セキュリティのギャップが特定されました。モデル エンドポイントにサービスを提供するワークロード VM に NSG が適用されておらず、インターネット上のどのポートからも直接アクセス可能です。 ワークロード サブネットからの送信トラフィックは、検査やフィルタリングなしで直接インターネットにルーティングされます。 推論サービスが使用するバックエンド ストレージ アカウントも公開されており、有効な SAS トークンを持つアクターならどこからでもアクセス可能です。

あなたのタスクは、3 つのギャップすべてを埋めることです。 ここでは、アプリケーション セキュリティ グループを使用してワークロード VM への受信トラフィックを制限する NSG ルールを適用し、ハブ ネットワーク内に Azure Firewall をデプロイし、これを経由してすべてのスポーク送信トラフィックをルーティングし、ストレージ アカウントのパブリック URL からアクセスできないようにプライベート エンドポイントを構成します。

このラボでは、次のことを行います。

- Azure Firewall のデプロイを事前に開始する (プロビジョニングに 10 〜 15 分かかります)
- アプリケーション セキュリティ グループと、ワークロードの VM トラフィックを制限する NSG ルールを作成する
- ワークロード ストレージ アカウントのプライベート エンドポイントを構成する
- アプリケーション ルール コレクションとルート テーブルを備えた Azure Firewall の構成を完了する
- Network Watcher の IP フロー検証を使用してネットワーク セキュリティ制御を検証する

この演習の所要時間は約 **65** 分です。

## Azure Firewall のデプロイを開始する

> **注**: Azure Firewall のプロビジョニングには **10 〜 15 分** かかります。 NSG やプライベート エンドポイントのタスクの作業中にプロビジョニングがバックグラウンドで完了するように、このラボはファイアウォールのデプロイから開始します。 ファイアウォールの作業が完了するのを待たずに、次のセクションに進んでください。

Azure Firewall は、ハブスポーク ネットワーク内のすべてのリソースに対して集中的な送信トラフィック検査を提供する、マネージド、かつステートフルなネットワークのサービスとしてのファイアウォールです。 このラボでは、`sc500-lab2c-spoke-vnet` ワークロード サブネットからのすべての送信トラフィックが `sc500-lab2c-hub-vnet` のファイアウォールを経由してルーティングされることで、送信先が明示的なアプリケーション ルールで制御され、すべてのトラフィックが記録されることが保証されます。

1. **User1** の資格情報を使用して **Azure portal** (`https://portal.azure.com`) にサインインします。

1. 検索バーで、「**ファイアウォール**」を検索して選択します。

1. **[+ 作成]** を選択します。

1. **[基本]** タブで次の値を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **リソース グループ** | sc500-lab2c-rg |
    | **名前** | `sc500-lab2c-fw` |
    | **リージョン** | ラボ セットアップ時に選択した Azure リージョン (ラボ環境で特に指示されない限り、米国東部) を使用します |
    | **可用性ゾーン** | なし |
    | **ファイアウォール SKU** | Standard |
    | **ファイアウォール管理** | ファイアウォール ポリシーを使用してこのファイアウォールを管理する |
    | **ファイアウォール ポリシー** | **[新規追加]** を選択し、`sc500-fw-policy` という名前を付け、**[標準]** レベルを選択して、**[OK]** を選択します |
    | **仮想ネットワークを選択する** | **[既存のものを使用]** を選択します |
    | **仮想ネットワーク** | sc500-lab2c-hub-vnet |
    | **パブリック IP アドレス** | **[新規追加]** を選択し、`sc500-lab2c-fw-pip` という名前を付け、**[OK]** を選択します |
    | **[ファイアウォール管理 NIC を有効にする]** | このチェックボックスはオフにしてください |


1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

    > **注**: ファイアウォールは現在デプロイ中です。 **完了するまで待たないでください。** すぐに次のセクションに進みましょう。NSG とプライベート エンドポイントのタスクはファイアウォールのデプロイとほぼ同じ時間で完了します。 ファイアウォールの構成は後のセクションで再度行います。

## アプリケーション セキュリティ グループと NSG ルールを作成する

**アプリケーション セキュリティ グループ (ASG)** は、VM が再デプロイされると変わる IP アドレスを使用する代わりに、NSG ルールで参照可能な論理ワークロード ID を仮想マシンにタグ付けします。 ワークロード サブネットに **NSG** がアタッチされると、ASG を名前で参照するトラフィック ルールが適用され、インフラストラクチャの変更に対してルールの回復性が高まります。

ワークロード VM (**sc500-lab2c-vm**) には現在 NSG が適用されていません。 どのポートでも、どのソースからもアクセスできます。 ここでは、AI 推論サービス用の ASG を作成し、インターネットからの受信 RDP を拒否し、仮想ネットワーク内からの受信 HTTPS を許可するルールを持つ NSG を作成し、その NSG をワークロード サブネットに適用します。

### アプリケーション セキュリティ グループを作成する

1. Azure portal の検索バーで、「**アプリケーション セキュリティ グループ**」を検索して選択します。

1. **[+ 作成]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **リソース グループ** | sc500-lab2c-rg |
    | **名前** | `sc500-asg-ai-inference` |
    | **リージョン** | ラボ セットアップ時に選択した Azure リージョン (ラボ環境で特に指示されない限り、米国東部) を使用します |

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

### ASG と VM を関連付ける

1. Azure portal の検索バーで、「**仮想マシン**」を検索して選択します。

1. **[sc500-lab2c-vm]** を選択します。

1. 左メニューの **[ネットワーク]** で **[アプリケーション セキュリティ グループ]** を選択します。

1. **[+ アプリケーション セキュリティ グループの追加]** を選択します。

1. **[sc500-asg-ai-inference]** を選択し、次に **[追加]** を選択します。

### NSG の作成

1. Azure portal の検索バーで、「**ネットワーク セキュリティ グループ**」を検索して選択します。

1. **[+ 作成]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **リソース グループ** | sc500-lab2c-rg |
    | **名前** | `sc500-lab2c-nsg` |
    | **リージョン** | ラボ セットアップ時に選択した Azure リージョン (ラボ環境で特に指示されない限り、米国東部) を使用します |

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

1. **[リソースに移動]** を選択して新しい NSG を開きます。

### 受信セキュリティ規則を追加する

1. `sc500-lab2c-nsg` の左メニューの **[設定]** で、**[受信セキュリティ規則]** を選択します。

1. **[+ 追加]** を選択します。

1. インターネットからの受信 RDP を拒否する、次の最初の規則を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **ソース** | [任意] |
    | **ソース ポート範囲** | * |
    | **宛先** | アプリケーション セキュリティ グループ、[sc500-asg-ai-inference] を選択する |
    | **サービス** | RDP |
    | **アクション** | Deny |
    | **優先順位** | 100 |
    | **名前** | `DenyInboundRDP` |

1. **[追加]** を選択します。

1. **[+ 追加]** をもう一度選択します。

1. 仮想ネットワークからの受信 HTTPS を許可する次の 2 つ目の規則を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **ソース** | サービス タブ、[仮想ネットワーク] を選択する |
    | **ソース ポート範囲** | * |
    | **宛先** | アプリケーション セキュリティ グループ、[sc500-asg-ai-inference] を選択する |
    | **サービス** | HTTPS |
    | **アクション** | Allow |
    | **優先順位** | 200 |
    | **名前** | `AllowInboundHTTPS` |

1. **[追加]** を選択します。

### NSG をワークロード サブネットに適用する

1. `sc500-lab2c-nsg` の左メニューの **[設定]** で、**[サブネット]** を選択します。

1. **[+ 関連付け]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **仮想ネットワーク** | sc500-lab2c-spoke-vnet |
    | **サブネット** | workload-subnet |

1. **[OK]** を選択します。

    > **注**: NSG を (個々の NIC ではなく) **サブネット**に関連付けることで、`workload-subnet` にデプロイされたすべての VM が同じセキュリティ規則を継承することが保証されます。 ASG を参照する規則は、`sc500-asg-ai-inference` に関連付けられた VM にのみ適用され、サブネット内の他のすべての VM は既定の規則のみが対象となります。

## ストレージのプライベート エンドポイントを構成する

> **注**: デプロイされたストレージ アカウント名は、**`sc500lab2c`** で始まり 8 文字のラボ インスタンス サフィックスが続きます。 このラボ全体で、`<storage-account-name>` はそのアカウントを参照します。 それぞれの `sc500-lab2c-rg` リソース グループに 1 つのストレージ アカウントが存在します。

ワークロード ストレージ アカウント (`<storage-account-name>`) は現在、どのネットワークからもパブリック エンドポイントを通じてアクセス可能です。 ここでは、`workload-subnet` に直接ストレージ アカウントのプライベート IP を置くプライベート エンドポイントを作成した後、パブリック アクセスを無効にして VNet 内からのみアカウントにアクセスできるようにします。

1. Azure portal の検索バーで、「**ストレージ アカウント**」を検索して選択します。

1. **<storage-account-name>** を選択します。

1. 左メニューの **[セキュリティとネットワーク]** で、**[ネットワーク]** を選択します。

1. **[パブリック アクセス]** タブで **[管理]** を選択して、公衆ネットワーク アクセスが現在有効になっていることを確認します。 パネルを閉じて、[ネットワーク] ページに戻ります。

1. **[プライベート エンドポイント]** タブを選択します。

1. **[+ プライベート エンドポイントの作成]** を選択します。

1. **[基本]** タブで次のように構成します。

    | 設定 | 値 |
    |---------|-------|
    | **リソース グループ** | sc500-lab2c-rg |
    | **名前** | `sc500-storage-pe` |
    | **リージョン** | ラボ セットアップ時に選択した Azure リージョン (ラボ環境で特に指示されない限り、米国東部) を使用します |

1. **[次へ: リソース]** を選択します。

1. **[リソース]** タブで、次を確認します。

    | 設定 | 値 |
    |---------|-------|
    | **リソースの種類** | Microsoft.Storage/storageAccounts |
    | **リソース** | <storage-account-name> |
    | **ターゲット サブリソース** | blob (blob) |

1. **[次へ: 仮想ネットワーク]** を選択します。

1. **[仮想ネットワーク]** タブ上で、次のように構成します。

    | 設定 | 値 |
    |---------|-------|
    | **仮想ネットワーク** | sc500-lab2c-spoke-vnet |
    | **サブネット** | workload-subnet |

1. **[次: DNS]** を選択します。

1. **[DNS]** タブで **[プライベート DNS ゾーンとの統合]** が **[はい]** に設定され、表示されている DNS ゾーンが **privatelink.blob.core.windows.net** であることを確認します。

    > **注**: `privatelink.blob.core.windows.net` のプライベート DNS ゾーンは事前にプロビジョニングされ、`sc500-lab2c-spoke-vnet` にリンクしていました。 プライベート エンドポイントが作成されると、このゾーンに自動的に A レコードが登録され、ストレージ アカウントの BLOB サービスの FQDN が新しいプライベート IP アドレスにマッピングされます。

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

    プライベート エンドポイントがデプロイされるまで (通常 1 〜 2 分) お待ちください。

1. `<storage-account-name>` の **[ネットワーク]** 設定に戻ります。

1. **[パブリック アクセス]** タブで、**[管理]** を選択します。

1. **[公衆ネットワーク アクセス]** を **[無効]** に設定した後、**[保存]** を選択します。

    > **注**: パブリック アクセスが無効になり、ストレージ アカウントがプライベート エンドポイントを通じて `sc500-lab2c-spoke-vnet` 内のリソースからのみアクセス可能になりました。 推論サービスの VM (`sc500-lab2c-vm`) はすべてのストレージ操作にプライベート IP を使用します。パブリック インターネットにはデータへのパスがありません。

## Azure Firewall の構成を完了する

ここまでで、Azure Firewall のデプロイは完了したか、ほぼ完了しているはずです。 まだデプロイ中なら、**[成功]** の状態になるまで待ってから続行してください。

ここでは、ワークロードの VM が Microsoft や Azure のサービス エンドポイントに到達できるようにアプリケーション ルール コレクションを追加し、スポーク サブネットからのすべての送信トラフィックをファイアウォール経由に強制するルート テーブルを作成します。

### ファイアウォールのデプロイを検証する

1. Azure portal の検索バーで、「**ファイアウォール**」を検索して選択します。

1. **[sc500-lab2c-fw]** を選択します。

1. **概要**ページで、プロビジョニング状態が **[成功]** と表示されていることを確認し、ファイアウォールの**プライベート IP アドレス**を書き留めます。 この IP アドレスは、ルート テーブルを作成する際に必要になります。

    > **注**: ファイアウォールのプライベート IP アドレスをテキスト ファイルにコピーしてください。 `10.3.1.x` (`AzureFirewallSubnet` 範囲のアドレス) のようになります。

### アプリケーション規則コレクションを追加する

1. `sc500-lab2c-fw` の**概要**ページで、**[ファイアウォール ポリシー]** フィールドを検索し、**[sc500-fw-policy]** を選択してポリシーを開きます。

1. `sc500-fw-policy` の左メニューの **[ルール]** で **[アプリケーション ルール]** を選択します。

1. **[+ 規則コレクションの追加]** を選択します。

1. 次のように、ルール コレクションを構成します。

    | 設定 | 値 |
    |---------|-------|
    | **名前** | `sc500-allow-outbound` |
    | **規則コレクションの種類** | アプリケーション |
    | **優先順位** | `100` |
    | **規則コレクションのアクション** | 許可 |

1. **[ルール]** で、次のルールを追加します。

    | 設定 | 値 |
    |---------|-------|
    | **名前** | `AllowMicrosoftEndpoints` |
    | **ソースの種類** | IP アドレス |
    | **ソース** | `10.4.0.0/16` |
    | **プロトコル** | `https:443` |
    | **送信先の種類** | FQDN |
    | **宛先** | `*.microsoft.com, *.azure.com, *.windows.net` |

1. **[追加]** を選択します。

    > **注**: このルールによって、スポーク VNet アドレス空間全体から Microsoft 所有の FQDN パターンへの送信 HTTPS トラフィックが許可されます。 運用環境では、`*.azure.com` のすべての宛先を許可するのではなく、ワークロードに必要な特定のエンドポイント (たとえば、Azure Cognitive Services や Foundry のエンドポイント) に絞り込むことができます。

### トラフィックをファイアウォールを経由するように強制するルート テーブルを作成する

1. Azure portal の検索バーで「**ルート テーブル**」を検索して選択します。

1. **[+ 作成]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **リソース グループ** | sc500-lab2c-rg |
    | **名前** | `sc500-spoke-rt` |
    | **ゲートウェイのルートを伝達する** | いいえ |
    | **リージョン** | ラボ セットアップ時に選択した Azure リージョン (ラボ環境で特に指示されない限り、米国東部) を使用します |

1. **[確認と作成](確認と作成)** を選択し、次に **[作成]** を選択します。

1. **[リソースに移動]** を選択してルート テーブルを開きます。

1. 左メニューの **[設定]** で、**[ルート]** を選択します。

1. **[+ 追加]** を選択します。

1. 次のように、既定のルートを構成します。

    | 設定 | 値 |
    |---------|-------|
    | **ルート名** | `DefaultToFirewall` |
    | **送信先の種類** | [IP アドレス] |
    | **宛先 IP アドレス/CIDR 範囲** | 0.0.0.0/0 |
    | **次ホップの種類** | 仮想アプライアンス |
    | **次ホップ アドレス** | (前に記録した) ファイアウォールのプライベート IP アドレス |

1. **[追加]** を選択します。

1. 左メニューの **[サブネット]** を選択します。

1. **[+ 関連付け]** を選択します。

1. 次を構成します。

    | 設定 | 値 |
    |---------|-------|
    | **仮想ネットワーク** | sc500-lab2c-spoke-vnet |
    | **サブネット** | workload-subnet |

1. **[OK]** を選択します。

    > **注**: このルート テーブルが設定されていると、`workload-subnet` からのすべての送信トラフィック (パブリック インターネットへのトラフィックを含む) は、スポーク ネットワークを離れる前に `sc500-lab2c-fw` を通過するように強制されます。 ファイアウォールのアプリケーション ルールに合致するトラフィックのみが通過を許可されます。 他のすべての宛先はファイアウォールの既定の拒否態勢によって暗黙的に拒否されます。

## Network Watcher でネットワーク セキュリティ制御を検証する

Network Watcher の **IP フロー検証**ツールは、VM のネットワーク インターフェイスに適用される有効な NSG ルールによって特定のトラフィック フローが許可されるか拒否されるかをテストします。 これは、作成した NSG によって受信 RDP がブロックされていること、そして受信 HTTPS が許可されていることを確認するために使用します。

1. Azure portal の検索バーで、「**Network Watcher**」を検索して選択します。

1. 左メニューの **[ネットワーク診断ツール]** で、**[IP フロー検証]** を選択します。

1. 受信 RDP をテストするために、次のように構成します。

    | 設定 | Value |
    |---------|-------|
    | **仮想マシン** | sc500-lab2c-vm |
    | **ネットワーク インターフェイス** | sc500-lab2c-vm の NIC を選択する |
    | **プロトコル** | TCP |
    | **方向** | インバウンド |
    | **ローカル IP アドレス** | VM の自動検出されたプライベート IP のままにする |
    | **ローカル ポート** | `3389` |
    | **リモート IP アドレス** | `8.8.8.8` (パブリック インターネットの IP) |
    | **リモート ポート** | `60000` |

1. **[IP フローの検証]** を選択します。 次に、ページの一番下までスクロールすると、ボタンの下にメッセージがあります。

    結果が **[アクセス拒否]** と表示されており、その原因となるルールとして `DenyInboundRDP` が特定されていることを確認します。

2. **[ローカル ポート]** を `443` に変更し、再度 **[IP フローの検証]** を選択します。

    結果が **[アクセス許可]** と表示されており、その原因となるルールとして `AllowInboundHTTPS` が特定されていることを確認します。

    > **注**: IP フロー検証では、有効なセキュリティ規則、つまり NIC レベルとサブネット レベルで適用されるすべての NSG を組み合わせた結果を評価します。 実際のトラフィックはテストしません。NSG 評価ロジックをシミュレートします。 これにより、実際のトラフィックでテストする前にファイアウォール規則が正しく構成されていることを迅速かつ非破壊的な方法で検証できます。

3. **Network Watcher** の左メニューで、**[有効なセキュリティ規則]** (**[ネットワーク診断ツール]** の下) を選択します。

4. **[sc500-lab2c-vm]** とそのネットワーク インターフェイスを選択します。 サブスクリプション、リソース グループ、VM、NIC のフィールドは自動的に入力されます。

5. **「ルール行をクリックして展開されたプレフィックスのリストを表示する」** セクションで、**[sc500-lab2c-nsg]** を選択して、受信および送信のルール リストを展開します。

6. **[受信]** ルールのリストに次のルールが表示されることを確認します。

    | Priority | Name | アクション |
    |----------|------|--------|
    | 100 | DenyInboundRDP | 拒否 |
    | 200 | AllowInboundHTTPS | Allow |

    Azure の既定のルール (65000 の `AllowVnetInBound`、65001 の `AllowAzureLoadBalancerInBound`、65500 の `DenyAllInBound`) は、カスタム ルールの下に表示されます。 これにより、あなたのルールが最初に評価されていることを確認できます — 優先度 100 や 200 に合致するトラフィックは既定値に到達しません。

## まとめ

このラボでは、ネットワーク制限のない AI ワークロード環境に 3 層のネットワーク セキュリティ制御を適用しました。

**アプリケーション セキュリティ グループ**を作成してワークロード VM に論理 ID のタグを付け、インターネットからの受信 RDP を拒否し、仮想ネットワーク内からの受信 HTTPS を許可するルールを持つ **NSG** を作成しました。 NSG をサブネットにアタッチすることで、`workload-subnet` の現在および将来のすべての VM がこれらのルールを継承することが保証されます。 **Network Watcher の IP フロー検証**を使用して、実際のトラフィックを生成しなくてもルールによって予期された許可/拒否の結果が生じることを確認しました。

ハブ ネットワークに **Azure Firewall** をデプロイし、ワークロード サブネットが HTTPS 経由で Microsoft や Azure のサービス エンドポイントに到達できるアプリケーション ルール コレクションを構成しました。 ファイアウォールのプライベート IP を指向する既定のルートを持つルート テーブルは、すべての送信スポーク トラフィックにファイアウォールを経由するように強制します。アプリケーション ルールで明示的に許可されていない送信先は拒否されます。

`workload-subnet` のワークロード ストレージ アカウントに**プライベート エンドポイント**を構成し、パブリック アクセスを無効にしたため、ストレージ アカウントは VNet 内のリソースからプライベート IP を通じてのみアクセス可能になりました。 事前プロビジョニングされたプライベート DNS ゾーンにより、スポーク VNet 内のクライアントはストレージ アカウントの FQDN をパブリック エンドポイントではなくプライベート エンドポイントのアドレスに解決するようになります。
